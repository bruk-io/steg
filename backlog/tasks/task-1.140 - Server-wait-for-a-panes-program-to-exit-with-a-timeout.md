## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Split from TASK-1.90 by its plan on 2026-11-18 (its third criterion). doc-2 sections 6 and 8: pane wait --for exit exits 0 when the program ended and prints the program's own exit code in its result; a wait that times out is status 1. TASK-1.90's plan holds the worked design as a starting point: pending waits kept in the runtime's state and resolved from the code paths that already hold the lock when a program exits or a pane is closed, with a timer only when a timeout is given that wakes at once on resolution. It needs a new module in crates/server/src/runtime/ that TASK-1.131's map did not anticipate, and probably a new error code for the timeout, which is a change to the API description for the engineer to agree. Built after pane send and pane capture: all three land in crates/server/src/dispatch/pane.rs.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 pane wait answers when the pane's program exits, with its exit code, or when the timeout given passes; a wait on a pane whose program has already ended answers at once; a pane closed while being waited on answers at once
- [ ] #2 A waiting request holds neither the runtime's lock nor a connection's reader; the plan says how the request is held and answered now that a reply is written by the connection's writer
- [ ] #3 A client that disconnects while waiting leaves no thread, timer or registration behind, shown by a test
- [ ] #4 pane wait leaves the not-yet list in dispatch; it is proved with a real program in a real pty and bounded waits, and what the timeout answers (its code and the CLI's exit status under doc-2 section 6) is settled with the engineer in the plan

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Starting point: TASK-1.90's own stale plan (§4, written 2026-11-18, before the split) already worked this design out in detail and is re-checked against the tree today, not re-derived from scratch. Re-checked facts: pane.wait is already fully described (crates/sdk/src/description/methods/pane.rs - target, for=Choice(["exit"]) required, timeout: Integer (seconds, doc-2 section 5) optional, Returns::Record{exit_code}, errors today BadRequest/NoSuchTarget/AmbiguousTarget only - no TimedOut); dispatch/pane.rs's "wait" arm and pane::HANDLED still list it, still answering NotImplementedYet citing this task; cross_cutting.rs:90 still expects that; TASK-1.88 (server.*/client.*) has since landed, so the ErrorCode-enum collision the stale plan flagged is gone. pane.capture landed (TASK-1.139) with the exact hand-off shape (CaptureSender/CAPTURE_TIMEOUT) the stale plan predicted, confirming the sibling precedent is sound; wait touches none of that code.

Not a split: one coherent cross-cutting mechanism (new runtime state, three resolution sites, one connection-level interception); the acceptance criteria are already scoped to exactly this.

DESIGN

Core decision, unchanged from the stale plan: pending waits live in Runtime's own state, resolved from the code paths that already hold its lock when the outcome becomes known (a real exit, a close), with a timer thread only when --timeout is given, woken early by a condition variable rather than ever sleeping out a timeout that is already answered. No worker-thread command, no polling loop, anywhere.

One deliberate simplification over the stale plan: its WaitGate carried the outcome through a `Mutex<Option<T>>`. It doesn't need to - whichever resolver fires first (the exit-event drain, the close path, or a real timeout) writes the real reply straight to the wait's own `Arc<Outbound>` and that is the only place the answer ever lives. The gate's only job is waking a sleeping timer thread early so it doesn't sit out the rest of a timeout whose answer is already known. So:

- `crates/server/src/runtime/wait.rs` (new - the seam TASK-1.131's own module map didn't anticipate, named as such in the task's own description):
  - `struct WaitGate { state: Mutex<bool>, changed: Condvar }` - `resolve()` sets `true` and notifies; `wait(timeout)` blocks on `wait_timeout_while(|done| !*done)` and returns nothing (the caller always re-checks the real state afterward - see below - so there is nothing useful to return here).
  - `struct PendingWait { request_id: u64, client_id: ClientId, outbound: Arc<Outbound>, gate: Option<Arc<WaitGate>> }` - `gate` is `Some` only when `--timeout` was given.
  - `pub(super) type PendingWaits = HashMap<PaneId, Vec<PendingWait>>` - a `Vec` because more than one client can wait on the same pane, and the same client can issue more than one wait on it (each its own `request_id`).
  - `pub(super) fn resolve_pane_waits_locked(state: &mut State, pane: PaneId, outcome: Result<i32, ApiError>)` - called with `state` already locked: `remove`s every `PendingWait` for `pane`, and for each one builds `Response::Ok(json!({"exit_code": code}))` or `Response::Error(error.clone())` from `outcome`, writes it with `Connection::reply(request_id, ...)` onto `wait.outbound`, and calls `gate.resolve()` on every one that has a gate, so its timer thread wakes now instead of at its own deadline. A failed `enqueue_control` here is best-effort and silently dropped (`let _ = ...`), the same tolerance `attach_pane` already documents - deliberately **not** `broadcast`'s own "shut the socket down" response to a full queue: `broadcast` fans one event out to every subscriber and must stop a slow one from piling up unboundedly; a wait's reply is a single, one-shot, point-to-point answer, so a failed enqueue here only means the connection's own outbound is already closed (nothing left to tell) or already full past `CONTROL_CAP` (256 other undelivered replies ahead of it - a connection in that state is not being read at all and is already on its way to being torn down by the existing stuck-writer/shutdown machinery `connection.rs`'s own doc describes, not something this mechanism needs to additionally detect).
  - `fn timeout_wait_locked(state: &Arc<Mutex<State>>, pane: PaneId, request_id: u64, client_id: ClientId)` - locks, finds and removes the one `PendingWait` in `pending_waits[pane]` matching `(request_id, client_id)` (several waits can be pending on the same pane - matching both, not just the pane, is what keeps them independent), and if it was still there, replies `ErrorCode::TimedOut` (open question #1, below) on its own outbound. If it is already gone (the exit/close path resolved it first, in the race between that path dropping the lock and this thread waking), this is a no-op - never a reply sent twice.
  - `impl Runtime { fn register_wait(&self, description, context, request, waiting: Waiting, outbound: &Arc<Outbound>) }`, `Waiting { client: ClientId, id: u64 }` grouped the same way `Attaching` groups `attach_pane`'s own three identifying values, for the same clippy argument-count reason. Body, closely mirroring `attach_pane`'s own shape (validate, lock, resolve, release, no lock held across anything that can block):
    - `validate(description, request)?` (as `ApiError`); on `Err`, reply it on `outbound` (same best-effort tolerance above) and return - the same self-enqueuing shape `attach_pane` already uses, so `connection.rs`'s own arm is a single call with nothing left to build.
    - Lock. `dispatch::target_pane(&state.tree, context, request)` - on `Err`, reply it and return (unlocked first).
    - Read the pane's own `Pane::program_status()` the same way `dispatch::pane::show`'s `record_for` already does (via `tree.tab_of_pane` + `find_tab`/`tab.pane`, both already `pub(crate)` from `dispatch::lookup`).
    - `Some(ProgramStatus::Ended{exit_code})`: reply `Ok({"exit_code": exit_code})` at once, no registration at all (AC #1's "already ended... answers at once").
    - `Some(ProgramStatus::Running)` (the only other case reachable in practice - a pane with no program at all would mean `None`, and every pane in the tree has one started under the same lock it was minted, `close.rs`'s own documented invariant; kept, not special-cased, since nothing sane changes if it were somehow reached - it is simply never deferred into a wait that could never resolve): parse `timeout` (seconds, doc-2 section 5) via `dispatch::param_i64(request, "timeout")`, building `Duration::from_secs(seconds.max(0) as u64)` - clamping a given value `<= 0` to an immediate timeout rather than refusing it (open question #2, below). Build `gate = timeout.map(|_| Arc::new(WaitGate::new()))`, push `PendingWait { request_id: waiting.id, client_id: waiting.client, outbound: Arc::clone(outbound), gate: gate.clone() }` into `state.pending_waits.entry(pane).or_default()`, drop the lock, and only then, if `(timeout, gate)` are both `Some`, `thread::spawn` a detached thread holding `Arc::clone(&self.state)` (the same `Arc<Mutex<State>>` clone the drain thread's own spawn already closes over - the precedented way this crate hands a background thread something Send+'static without handing it `&Runtime`, which the connection's own stack frame cannot promise outlives it) that calls `gate.wait(timeout)` then unconditionally calls `timeout_wait_locked` (itself the no-op-if-already-resolved check, so there is nothing to branch on here).
  - `impl Runtime { fn cancel_waits(&self, client_id: ClientId) }` - locks once, and for every pane's `Vec<PendingWait>` removes every entry whose `client_id` matches (via `retain`, calling `gate.resolve()` on each removed one with a gate before dropping it). No reply is ever sent here - the connection is already gone.
  - `pub(crate) fn pending_wait_count_for_test(&self, pane: PaneId) -> usize` - **not** `#[cfg(test)]`, the same way `attachment_count_for_test` already isn't: compiled into the crate unconditionally, visible to this crate's own `#[cfg(test)] mod tests` (e.g. in `connection.rs`), never exported to an external `tests/` integration binary, which only ever sees the public API.

- `crates/server/src/runtime/mod.rs`: `mod wait;` added to the module list; `pub(crate) use wait::Waiting;` added alongside the existing `pub(crate) use attach::Attaching;`. `State` gains `pending_waits: wait::PendingWaits`, initialised empty in `Runtime::new`.

- `crates/server/src/runtime/events.rs`, `apply_event_locked`'s `PaneEvent::Exited` arm: as the first statement inside the existing `Ok(outcome) => { ... }` block (ahead of the `broadcast`/cascade code, unchanged below it), `super::wait::resolve_pane_waits_locked(state, pane, Ok(exit_code))` - correct regardless of whether `outcome` is `Stayed` or `Closed`, since a wait only ever cares about the exit code, not the cascade. The `Err(PaneNotFound(_))` arm needs no change: by the time that race is reachable (a forced close's own grace window - see `close.rs` below), `close_and_dispatch` has already drained this pane's waits itself, under the lock it used to remove the pane from the tree, so there is nothing left here to resolve a second time.

- `crates/server/src/runtime/close.rs`, `close_and_dispatch`: right after `emit_close_events(...)` and before `scope.into_iter()` builds `to_force` (still under the lock, with `scope: Vec<PaneId>` still owned - only borrowed here), for `&pane in &scope { wait::resolve_pane_waits_locked(&mut state, pane, Err(pane_closed_while_waiting())) }` - a new small helper `fn pane_closed_while_waiting() -> ApiError` (`ErrorCode::NoSuchTarget` - already in `pane.wait`'s own `errors:` list today, so this one needs **no** description change at all, unlike the timeout case below: doc-2's own answer for "the thing you asked about is gone," and `pane.wait`'s `Returns::Record{exit_code}` has nothing honest to put there for a pane that was closed rather than exited - the same reasoning `ClosedPane`/`EndReason::Closed` already carry no exit code for). Covers every path through this function - `pane.close`, `tab.close`, `session.close`, forced or plain - since `scope` is already exactly "every pane this close just removed from the tree," computed once above regardless of method. AC #1's "a pane closed while being waited on answers at once" - genuinely at once here: no extra thread, the same lock acquisition the close already needed, answered long before `force_end` (which runs after this, unlocked) would ever end the program.
  - `Runtime::stop` (server stop; `Drop for Runtime`) calls `force_end` directly against every pane, never through `close_and_dispatch`, so it never itself touches `pending_waits`. This is sound, not a gap: `server.stop`'s own connection returns `false` from its `handle_request` arm, running its own `ConnectionCleanup::drop` (which calls `cancel_waits`) before `Stopper::stop()` is even allowed to end the accept loop, and `listen::run`'s own existing shutdown pass then closes and joins every *other* connection the same way, each running its own `ConnectionCleanup::drop` in turn - so by the time `Runtime::stop`'s `force_end` actually runs, no connection with a pending wait on any pane is still attached to tell. Stated here so a reviewer does not have to re-derive it.

- `crates/server/src/connection.rs`:
  - `ConnectionCleanup::drop`: one new line, `self.runtime.cancel_waits(self.client_id);`, placed after the existing `pane_streams` sweep loop and before `deregister_subscriber`/`disconnect_client` - the same ordering reasoning already documented there (this client's id must still unambiguously mean this connection when it is cancelled). AC #3 in full: no reply sent (the connection is gone), the `PendingWait` entry is removed synchronously inside this one call (no polling needed to observe it gone), and any timer thread that exists for it wakes via its own gate and exits within its own bounded wait, never past it.
  - `handle_request`: one new arm, `"pane.wait" => { runtime.register_wait(description, context, &resolved, crate::runtime::Waiting { client: client_id, id }, outbound); true }` - placed with the other four interceptions (`pane.attach`/`pane.detach`/`tab.declare-size`/`server.stop`), for the identical structural reason stated on all of them: answering it needs this connection's own `Arc<Outbound>` and (new) the server's pending-wait state, neither reachable from `dispatch`'s plain `(&mut Tree, ...)` signature. `register_wait` already enqueues its own reply or registers and returns nothing further to send - `true` unconditionally, the same tolerance `pane.attach`'s own arm already has for a reply that failed to enqueue because the connection is concurrently tearing down.

- `crates/server/src/dispatch/pane.rs`: remove `("pane", "wait")` from `HANDLED`, and delete the `"wait" => Err(not_implemented_yet(...))` arm from this module's own `dispatch` match (now unreachable through this module at all, the same way `"send"`/`"capture"` stopped being matched here once their own tasks landed).

- `crates/server/src/dispatch/mod.rs`:
  - `dispatch_raw`: one new literal arm, next to `("pane", "attach" | "detach")`: `("pane", "wait") => Err(not_implemented_yet("connection.rs's own interception (TASK-1.140) - ... neither reachable from this function's signature"))` - the same "fully built, never reached this way in the real system" shape every other interception already documents.
  - `#[cfg(test)] const INTERCEPTED_BEFORE_DISPATCH`: add `("pane", "wait")`. `handled()`'s own completeness test needs no other change - `pane::HANDLED` losing the entry and `INTERCEPTED_BEFORE_DISPATCH` gaining it keeps the two lists' union exactly equal to `description().methods` either way.

- `crates/server/tests/dispatch/cross_cutting.rs:90`: the `("pane.wait", ..., "TASK-1.140")` row's expected substring becomes `"connection.rs's own interception"` - the same wording `"server.stop"`'s own row already uses, since `pane.wait` joins it as "described, fully built, never reached through `dispatch` directly."

sdk changes - **conditional on open question #1 below being agreed, not done unilaterally**: if agreed, add `ErrorCode::TimedOut` to shapes.rs, its `ErrorRecord` (methods/errors.rs, `exit_status: 1`) and to `pane.wait`'s own `errors:` list (methods/pane.rs); in methods/tests.rs, `errors_has_thirteen_codes_with_their_exit_statuses` becomes fourteen (rename the fn too) with one more `assert_eq!(status_of(ErrorCode::TimedOut), 1)`.

OPEN QUESTIONS FOR THE ENGINEER

1. **Blocking - a new error code for the timeout.** doc-2 gives `pane.wait`'s own timeout no code, only a CLI exit status (section 6: "a wait that times out is status 1"), and nothing in today's `ErrorCode` enum fits (checked directly against the full enum: `BadRequest`/`NoSuchTarget`/`AmbiguousTarget`/`ProgramRunning`/`ProgramNotRunning`/`PositionOutOfRange`/`SplitTooSmall`/`NoSplitInDirection`/`PanesNotInSameTab`/`AlreadyInTab`/`NotImplementedYet`/`EngineFailed`/`ProgramFailed` - none names "the wait itself gave up"). The task's own description calls this out explicitly ("probably a new error code for the timeout, which is a change to the API description for the engineer to agree") and AC #4 requires it be "settled with the engineer in the plan" - this is a real API-description change, not a detail this plan can decide alone, the same way `ProgramNotRunning` went to the engineer on TASK-1.90 before it was added. Recommend `ErrorCode::TimedOut` ("A wait reached its own timeout before the condition was met"), `exit_status: 1` (doc-2 section 6's own wording for this exact case, so no new CLI mapping is needed once TASK-1.50 exists). The task cannot be finished without this being agreed - everything above describing `TimedOut` is contingent on it. The *other* new-answer case, a pane closed while being waited on, needs **no** description change: it reuses `ErrorCode::NoSuchTarget`, already in `pane.wait`'s own `errors:` list today.
2. A `--timeout` of zero or negative: clamp to an immediate timeout rather than `BadRequest` - doc-2 is silent; flagged, not blocking.
3. The reply's own shape - a one-field `json!({"exit_code": exit_code})` built inline, versus a small typed `steg_sdk` struct (mirroring `PaneAttached`) per `rust.md`'s "typed struct at a boundary" rule: recommend the typed struct for consistency, but it is a one-line change either way if the engineer prefers the inline form.
4. `WaitGate`'s simplification from the stale plan's `Option<T>`-carrying gate to a bare wake signal (above) - named so a reviewer comparing against TASK-1.90's old plan doesn't go looking for a dropped payload.

PROOF PER ACCEPTANCE CRITERION

- AC #1: `crates/server/tests/pane_wait.rs` (new, real sockets, the same `support::{ScopedTempDir, scoped_socket_path}` + `start_server`/`stop_server` harness `pane_capture.rs`/`pane_send.rs` already use, real explicit pty programs, never `$SHELL`/`$HOME`, every wait bounded):
  - a wait on an already-ended pane (waited into that state via a real exit, never a sleep) answers at once with the real exit code.
  - a wait on a running pane answers once a real program really exits, with its real code.
  - a wait with `--timeout` against a program that outlives it answers `TimedOut` within the bound.
  - closing the pane (or its tab/session, with `--force`) while a wait is pending answers `NoSuchTarget`, bounded well under `force_end`'s own grace window - proving the close-path resolution fires immediately under the lock, not only once the program is actually made to die.
  - negative controls: (exit) with `resolve_pane_waits_locked`'s call removed from the `Exited` arm, the first two cases hang past a generous bound - recorded failing then passing; (close) with the same call removed from `close_and_dispatch`, the fourth case instead blocks for the close's own grace window - recorded failing then passing; (timeout) with `gate.resolve()` removed from `resolve_pane_waits_locked`'s own loop (only meaningful if a timer thread for the same wait is concurrently sleeping - noted explicitly if the test as built never actually exercises that overlap, rather than claimed unproven).
- AC #2: same file - a `pane.wait` sent with no timeout against a running pane, then, on the very same connection, an unrelated request (e.g. `pane.list`) sent right behind it without waiting for the first reply: the second reply must arrive (bounded) while the first is still outstanding, proving `register_wait` released the lock and the connection's own reader never blocked on the pending wait. Negative control: temporarily holding `state`'s lock across a `thread::sleep` inside `register_wait` (scratch edit, reverted) stalls the second request past the bound - recorded, not committed.
- AC #3: a same-crate unit test (`crates/server/src/connection.rs`'s own `#[cfg(test)] mod tests`, the identical shape `connection_cleanups_drop_sweeps_every_attachment_it_still_holds` already uses for attachments): register a pending wait directly through `runtime.register_wait` against a real, still-running pane, with a short timeout so a timer thread genuinely exists; build a `ConnectionCleanup` around it and drop it; assert `runtime.pending_wait_count_for_test(pane) == 0` at once (synchronous - `cancel_waits` removes it under the same call, no polling needed) and that a *second*, fresh `pane.wait` against the same still-running pane (through `runtime.register_wait` again, a second connection's worth of identifying values) still registers and later resolves correctly once the pane really exits - proving the cancelled entry did not leave anything that would wedge a later wait, not merely that nothing crashed. Negative control: with the new `self.runtime.cancel_waits(self.client_id)` line removed from `ConnectionCleanup::drop`, `pending_wait_count_for_test(pane)` stays at 1 after the drop instead of reaching 0 - recorded failing then passing.
- AC #4: `pane.wait` is removed from `dispatch/pane.rs`'s `HANDLED` (so `cross_cutting.rs`'s completeness test no longer sees it as a `NotYetCase` citing this task) and both AC #1's tests above and AC #2/#3's use real ptys/real sockets throughout, with every wait bounded (`run_bounded`/explicit deadlines, never a bare sleep). The timeout's own code and the CLI's eventual exit status are settled above against doc-2 section 6 directly, flagged to the engineer (open question #1), not guessed at unilaterally.

RISK

The only genuinely new, cross-cutting state in the server is `pending_waits` itself - no existing precedent beyond `RunGate`'s own narrower, one-gate-per-run shape. Mitigated by keeping every resolution site a plain, already-lock-holding function call (no second lock, no new thread except the one, bounded, early-wakeable timer per timed wait) and by the same real-pty/real-socket proof style this crate's own `attach.rs`/`pane_send.rs`/`pane_capture.rs` already established. The sdk change (open question #1) is the one part of this task that is really an API-description change wearing a server task's name, same as TASK-1.90 flagged for `ProgramNotRunning` - worth the engineer's eyes before any of it lands.
