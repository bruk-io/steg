## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Agreed with the engineer on 2026-11-17. Several workers run just check on this machine at once, each with its own target directory, and the timing-sensitive server tests then fail for no reason of their own: on 2026-11-17 the login_env grandchild test failed in 4 of 6 runs with two workers checking, and a stuck-pane test and a terminal-scrolling test failed once each under the same load. This is the ceiling on how many workers can usefully run. tools/src/steg_tools/quiet.py already wraps every step and is the natural place. TASK-1.123 bounds the waits; this task lowers the load that makes them matter.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The heavy steps of just check and just test take a machine-wide slot before they run; at most two run at once by default, and an environment variable sets the number
- [ ] #2 A run that is waiting says so in one line, naming what it waits for, and waits on the lock itself with no polling or timer
- [ ] #3 A run that crashes or is killed frees its slot without anyone cleaning up, because the operating system holds the lock
- [ ] #4 CI is unaffected; the tools' own tests cover two runs contending for one slot, a freed slot being taken, and the variable, each with a recorded failing control
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Mechanism: a gate lock plus N slot locks under one directory, taken per heavy step inside tools/src/steg_tools/quiet.py.

1. WHAT TAKES A SLOT: each heavy step, not the whole run. `just check`/`just test`/`just test-all` run their recipe dependencies sequentially (just's default), so one worktree's own run already serialises its own heavy steps internally; the real machine-wide contention is across separate `just check` processes (different workers/worktrees) overlapping. Per-step locking therefore already caps "N heavy cargo processes machine-wide" exactly, while letting cheap steps (fmt check, boundaries, deny, foundations/design/architecture/recipes/ui-levels/ui-colours - all `uv run` Python tools) interleave freely across workers instead of queueing behind an idle run holding a whole-run slot. "Heavy" = detected by inspecting the command vector already passed to `steg-quiet <label> -- <command>`: `command[0] == "cargo" and command[1] in {"build", "test", "clippy"}`. This covers `lint` (clippy), `test`, `test-all`, every `cargo build -p`/`cargo test -p` call inside `check-packages`'s loop, and `build`; it excludes `cargo fmt --check` and `cargo deny check licenses` (metadata only). No justfile recipe bodies change: detection lives entirely in quiet.py by inspecting the command it is already given, so ~14 call sites (check-packages' loop) need no individual edits.

2. THE LOCK DIRECTORY: `lock_directory(env) -> Path`, pure function. `STEG_CHECK_SLOTS_DIR` overrides everything (also how tests point at tmp_path); otherwise `$XDG_CACHE_HOME/steg/check-slots` if set, else `~/.cache/steg/check-slots`. Per-user, per-machine, local disk by default, outside every worktree so all worktrees of this repo (and any other steg checkout on the same machine) share it. Never keyed off `$TMPDIR`: it can differ between sandboxed shells on the same machine, which would silently defeat the limiter while appearing to work. A stale directory or stale lock files are harmless and need no cleanup: flock state lives in the kernel against the open file description, not in the file's bytes or mtime, so an empty leftover lock file from a previous boot is inert and reused forever.

3. THE WAIT, WITH NO POLLING: `gate.lock` plus `slot-0.lock` .. `slot-(N-1).lock` in that directory, each opened once per step with `os.open(..., os.O_CREAT | os.O_RDWR)` (Python's PEP 446 default makes every fd it opens close-on-exec already, see #6).
   - Block on the gate: `fcntl.flock(gate_fd, fcntl.LOCK_EX)` - a single blocking syscall, no polling.
   - Under the gate, one non-blocking pass over the N slot fds in order with `LOCK_EX | LOCK_NB`; first success wins, release the gate immediately, run holding that slot.
   - If all N are busy: print the one wait line (see #5), release the gate, then `fcntl.flock(slot_fds[0], fcntl.LOCK_EX)` - block on slot 0 specifically, always, by a fixed stable rule, never a different slot per waiter. This is the single blocking syscall that is "the wait"; still no polling, no timer, by default.
   - No deadlock: a slot holder never touches the gate again until it releases its own slot, so there is no cycle between the gate and any slot. At most one process is scanning/deciding at a time (serialised by the gate itself, which is always grantable in bounded time); every other process is either running with a held slot or blocked on slot 0, and slot 0 is guaranteed to be released (by its holder finishing, bounded by STEG_QUIET_TIMEOUT_S/900s, or by that holder being killed, which also releases it - see #3b) in finite time.
   - Disclosed cost, stated plainly rather than hidden: a waiter that reaches the "all busy" branch commits to slot 0 even if slot 1..N-1 frees first; it does not get redirected. Under sustained contention with more waiters than slots, slot 1..N-1 can sit free for the rest of slot 0's current step with no one blocked on it, used only by a brand-new arrival that happens to scan while it is free. Per-step scoping bounds this: the wasted idle time is at most one more heavy step's duration (bounded by STEG_QUIET_TIMEOUT_S), not unbounded, so this is acceptable without being invisible.
   - Rejected alternatives, and why: a POSIX/`multiprocessing` semaphore gives one real "wait for any of N" call, but a SIGKILLed holder never posts back to it, permanently losing a slot - fails AC #3. A token FIFO (N bytes, blocking `read`) fails the same way, worse (a lost token has no owner to even suspect). A SysV semaphore with `SEM_UNDO` is the one primitive that gives both a single blocking "any of N" call and kernel-reversed release on a killed holder, but needs a ctypes/libc binding (no stdlib wrapper) and has its own macOS/Linux sysv-limits quirks; offered here as the engineer's call for a future task, not chosen for this size-2 one. Hashing to one fixed slot per process (e.g. `pid % N`) is simpler than the gate but strictly worse utilisation: it can block a waiter on a specific slot that is not free yet even at the instant another slot sits idle, which the gate+scan never does, since the scan always takes whichever slot is free *right now*.

3b. ACQUIRE AROUND THE STEP, NOT INSIDE IT: the slot is taken in `main()`, wrapping the existing call to `run_captured`/`run_live`, never inside those functions. `run_captured` starts `STEG_QUIET_TIMEOUT_S`'s clock (`time.monotonic()`) immediately before `Popen`; if the slot wait happened inside that window, a queued step would be charged against the 900s bound and could report a false `TIMED OUT` for a job that had not even started. The wait is therefore unbounded with respect to that timeout by construction, not just by convention.

4. WHO HOLDS THE LOCK, AND WHY A KILL STILL RELEASES IT (AC #3): the slot fd is opened and held by the `steg-quiet` *parent* Python process, never by the `cargo ...` child it spawns. `run_captured`/`run_live` already call `Popen(..., start_new_session=True)`, making the child its own new process group leader; the parent (holding the fd) is not a member of that group. So `_kill_group`'s `killpg` on the 900s timeout kills the child's whole group and leaves the parent alone to write its TIMED OUT report and exit normally, releasing the slot then. If instead the *parent* itself is killed (e.g. a worker's own ten-minute Bash-tool timeout reaching the whole `just check` process tree), the kernel closes all its fds on process death, which releases the flock on that open file description immediately - no cleanup code, exactly AC #3's "because the operating system holds the lock." The lock must not be inherited by the `cargo` child: Python's PEP 446 makes every fd opened via `os.open`/`open` close-on-exec by default, and `subprocess.Popen`'s own default `close_fds=True` reinforces it - both already true with no extra flags, but call this out as intended, not accidental, since an inherited fd surviving in a cargo-spawned grandchild that outlives the killpg would hold the slot forever.

5. WHAT IS PRINTED: nothing extra on the fast path (quiet stays quiet). Only when the non-blocking scan under the gate finds all N busy, one line, flushed before the blocking call: `wait    <label> (N slots busy, STEG_CHECK_SLOTS=N) - waiting on slot 0`, matching the existing column style (`ok      `, `FAILED  `, `TIMED OUT `).

6. DEFAULT AND ENV VAR: `effective_slot_count(env) -> int | None` (None = unlimited, taking no lock at all - not even opening the directory): `STEG_CHECK_SLOTS` explicit and non-zero -> that integer (reject negative with a clear ValueError); `STEG_CHECK_SLOTS=0` -> None (no limit, used verbatim everywhere, including CI if someone sets it there on purpose); unset and `CI` is set (GitHub Actions sets `CI=true` always) -> None (CI's own `concurrency` group already runs at most one `check` job per ref, so the limiter adds lock-directory assumptions on an ephemeral runner for zero benefit); unset and no `CI` -> default 2. A pure function over a plain env mapping, unit-tested with dicts, no doubles.

7. BOUNDED WAIT, AGAINST THE AGENTS' OWN TEN-MINUTE FOREGROUND TIMEOUT (open question, my recommendation below): `flock` has no native timeout. Add one narrow, disclosed, OPT-IN exception to "no polling or timer": if `STEG_CHECK_SLOT_WAIT_S` is set, wrap only the single blocking `flock(slot_fds[0], LOCK_EX)` call with `signal.alarm`/a SIGALRM handler that raises; on expiry, fail the step with a message naming the bound, the lock directory, and both env vars, rather than silently proceeding unslotted (which would quietly defeat the feature). Default: unset, i.e. unbounded, true to AC #2's literal wording and to "wait on the lock itself" as the primary, always-on mechanism. OPEN QUESTION FOR THE ENGINEER: `check-packages` alone takes ~14 heavy slots in sequence, so a worker whose `just check` queues behind two others can exceed its own harness-side ten-minute foreground Bash timeout; the worker then just sees a generic tool timeout with no useful message, not this plan's clear "FAILED - gave up waiting Ns for a slot" text, because the bounded-wait message only fires if `STEG_CHECK_SLOT_WAIT_S` was set in that process's environment and stayed inside the bound. I recommend leaving the default unbounded (per above) and instead fixing this at the orchestration layer - worker briefs should run `just check` with `run_in_background` rather than foreground when slots are likely contended - rather than silently capping the wait by default in code, which would turn "waiting" into "failing" for a worker that simply arrived third. If the engineer wants a code-level default bound instead, `STEG_CHECK_SLOT_WAIT_S` is already the mechanism to set one fleet-wide via the environment with no further code change.

8. CTRL-C: a blocking `flock` is a normal interruptible C call; SIGINT's existing Python-level handler raises `KeyboardInterrupt` through it like any other blocking call, unwinding `main()` normally. No special-case code needed; the `finally` around the held slot still runs on that unwind, and even if it didn't, process exit releases the fd regardless.

9. FILES THAT CHANGE:
   - tools/src/steg_tools/quiet.py: pure functions `heavy_cargo_command(command)`, `effective_slot_count(env)`, `lock_directory(env)`; the `held_slot(lock_dir, count)` context manager (thin shell: real `os.open`/`fcntl.flock` I/O, parametrised so tests never touch the real default directory); the optional SIGALRM-bounded wait; wiring in `main()` around the existing `run_captured`/`run_live` calls; module docstring updated with the new behaviour and the two new env vars, in the same voice as the existing STEG_QUIET_TIMEOUT_S commentary.
   - tools/tests/unit/test_quiet.py: new tests for the three pure functions - `heavy_cargo_command` true for `[\"cargo\",\"build\",...]`/`[\"cargo\",\"test\",...]`/`[\"cargo\",\"clippy\",...]`, false for `[\"cargo\",\"fmt\",\"--check\"]`, `[\"cargo\",\"deny\",...]`, `[\"uv\",\"run\",...]`, and a single-element command; `effective_slot_count` for unset->2, explicit N, `\"0\"`->None, `CI` set with no override->None, `CI` set with an explicit override->that value, negative->raises; `lock_directory` for no override/no XDG->`~/.cache/steg/check-slots`, `XDG_CACHE_HOME` set, and `STEG_CHECK_SLOTS_DIR` override taking precedence over both.
   - tools/tests/functional/test_quiet_slots.py (new): real processes, real lock files, `STEG_CHECK_SLOTS_DIR` pointed at `tmp_path`, every wait in the test itself bounded (`subprocess.communicate(timeout=...)`, never a bare wait):
     a. two heavy steps with `STEG_CHECK_SLOTS=1` serialise - the second's observed start is at/after the first's observed end (each writes a timestamp file).
     b. the same scenario with `STEG_CHECK_SLOTS=0` overlaps instead - the second starts before the first ends. This is AC #4's required failing control for (a) made permanent: it proves the limiter, not accidental timing, caused the serialisation in (a), and it doubles as the direct proof that \"no limit\" behaves differently.
     c. a holder SIGKILLed mid-step (after it signals, via a file, that it has acquired) frees its slot promptly - a second process acquiring the same single slot completes within a short bounded `communicate(timeout=...)`, proving AC #3 without any cleanup code running.
     d. `STEG_CHECK_SLOTS=2` with three short heavy steps - two run immediately, the third waits for one of the first two, measured by the total wall time staying near two steps' duration rather than three serialised ones (generous tolerance).
     e. `STEG_CHECK_SLOTS=0` with a heavy step - the lock directory is never created at all (no `gate.lock`, no `slot-0.lock`) - proves \"no limit\" takes no lock, literally.
     f. a cheap (non-cargo-build/test/clippy) step runs immediately even while every heavy slot is held - proves the per-step scoping, that cheap steps never queue behind the limiter.
     Before the code exists, (a)-(f) are run and recorded failing (`asdlc record-check`) as the explicit before/after control the task's AC #4 asks for; after implementing, each is re-recorded passing.
   - justfile: one added line in the file's own top-of-file comment block (next to the existing `STEG_VERBOSE=1` note) naming `STEG_CHECK_SLOTS` (and `STEG_CHECK_SLOT_WAIT_S` if kept) and what each does.
   - No change to .github/workflows/ci.yml: CI is left alone by the `effective_slot_count` policy's own default (CI detected, unlimited unless the workflow opts in explicitly), not by special-casing the workflow file.

10. ORDER OF WORK: (1) the three pure functions + their unit tests, fast feedback, no I/O; (2) `held_slot` + wiring into `main()`, acquisition kept strictly outside `run_captured`/`run_live`'s own timing; (3) the optional SIGALRM-bounded wait, default off; (4) the functional tests against `tmp_path` via `STEG_CHECK_SLOTS_DIR`, recorded failing first, then passing; (5) the justfile comment line; (6) a sanity run of `just check` and `just test-tools` for real, to confirm nothing existing regresses (not itself proof of the new feature, which the functional tests already are).

11. RISKS: macOS and Linux both give `flock(2)` the same per-open-file-description semantics this design relies on (nothing macOS-specific beyond what quiet.py's own `killpg`/process-group handling already assumes). Network-mounted home directories make `flock()` correctness unreliable across hosts - not solved here; named as a known limitation, with `STEG_CHECK_SLOTS_DIR` as the escape hatch to point at local disk if ever hit. A stale lock directory or stale lock files are harmless by design (#2) - no cleanup code, so a reviewer should not expect any. `check-packages`'s own loop takes a slot on each of its ~14 sequential cargo build/test calls - deliberate, not 14 accidental acquisitions, each released before the next is taken, same as today's sequential behaviour just now also gated machine-wide. `test-openpty-race-control` (not part of `just check`) is `cargo test ... --features pty-race-fixture`, so the detection rule correctly treats it as heavy and it will take a slot when run by hand or recorded - harmless, arguably right (it is a real cargo test using real resources), noted so it does not read as a detection bug. `test-tools` itself runs `pytest`, never `cargo`, so it is never \"heavy\" and can never contend with - or self-deadlock against - the very slot machinery its own tests exercise.

12. NOT SPLITTING: the limiter, its wiring in quiet.py, and its tests are one coherent change; the one-line justfile comment documenting the variables is not a second change.
