## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A thin slice cut on 2026-11-16 at the engineer's request, to have something visible and usable early and to learn early whether GPUI can draw a terminal within the latency budget (doc-10's open question), before the components, the bar and the pane layout exist. Deliberately bare: one window, one session, one pane; no bar, no tabs, no splits, no palette, no settings, no selection or copy, no scrollback view, no events subscription (it makes its own session and attaches, so it needs TASK-1.47 and TASK-1.114 and not TASK-1.46). doc-9 R19; doc-10 R20, R22, R24; doc-13 R59 (the view is written fresh, nothing taken from GPL code); decision-3 section 5; decision-11 (GPUI directly, pinned at 0.2.2; read its README and the examples text.rs, text_layout.rs, input.rs and painting.rs against the pinned source). The terminal's cell drawing is the app's own and uses the foundations' terminal themes and fonts through the theme; it is not one of the component crate's four levels unless the plan finds it should be (doc-17, out of scope). What this leaves for TASK-1.56: the latency budget as a pass or fail on a 120 Hz display, the 100 MB flood with a second pane, font settings, a size set by another client, and fitting the view into the pane layout. What it leaves for TASK-1.52: the app holding what the server reports through events, a second window, and reconnecting.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Running the app opens one window showing one terminal: it starts a server if none is running, makes a session, attaches to its pane, and draws the pane's rows, colours and cursor from the attachment's snapshot and updates, in the terminal theme the foundations give for the system's light or dark setting
- [ ] #2 Typing reaches the program and its output is drawn: a shell prompt accepts a command and shows the result; keys that are text, Enter, Backspace, Tab, the arrows and Control combinations arrive as the bytes a terminal sends; resizing the window declares the new size and the program is told

## 1. Structure (a)

**Where the code lives.** `crates/app`, as a module tree, not `crates/ui`: doc-17 is explicit that the terminal's cell drawing "is the app's own and is not one of the component crate's four levels unless the plan finds it should be" (doc-17, "Out of scope"), and nothing here draws a reusable UI atom/molecule/organism — it is one bespoke element reading a wire shape (`steg_sdk::Screen`/`Row`/`Run`/`CellStyle`) no `steg-ui` component may know about (R118: "no type in the package's public interface names ... any other thing of steg's domain"). `steg-ui` supplies only values through `Theme` (R123): `foundations::steg_dark`/`steg_light`, `FONT_TERMINAL`/`TERMINAL`.

```
crates/app/src/
  main.rs            entry point: Application::run, opens the window once startup finishes
  startup.rs          part 1: connect/autostart, hello, find-or-make session, tab/pane list, attach — all
                       blocking sdk calls, run once on a background-executor task, off the main thread
  client.rs           part 1: owns the UnixStream + Connection after startup hands them over; the
                       non-blocking poll loop; part 2 adds declare_size/send_data's outbound half here
  model.rs            part 1: pure data — Vec<DrawRow> + Cursor + a fixed (columns, rows) read once
                       from the attach snapshot, `apply(&mut self, ScreenUpdate)`; part 2 adds tracking
                       (columns, rows) from each update's own `size` field instead of holding it fixed;
                       no gpui::Window/Context param anywhere in this file, in either part
  metrics.rs           part 1: pure data — CellMetrics (cell_width, line_height) from a shaped probe
                       string; `columns_rows(viewport: Size<Pixels>, metrics: &CellMetrics) -> (u16, u16)`
  terminal_element.rs  part 1 (read-only paint) / part 2 (adds on_key_down, resize-driven declare_size):
                       the Element impl — request_layout/prepaint/paint, the row-shaping cache
  keys.rs              part 2: pure data — `fn key_to_bytes(keystroke: &Keystroke) -> Vec<u8>`
  latency.rs           part 3: the probe — start/arrival/painted, blocks of percentiles, printed
```

Every file above `terminal_element.rs` and `client.rs`/`startup.rs` is plain data and functions with no `Window`/`Context`/`App` parameter — that is deliberate, and it is what makes §7's proof possible without gpui's test-support feature or a window at all.

**Layers and what crosses between threads.**

- *Startup (background-executor task, `cx.background_executor().spawn`, blocking, off the main thread — point 2 above is why this can't be synchronous in `main`'s own `Application::run` closure):* `steg_sdk::local_socket::connect` (autostart, the resolved binary, a few seconds' `connect_timeout`) → `Connection::send_hello`/write → block-read until `Incoming::Hello`, `parse_server_hello` → `Connection::call("session.list", {})`, find a record whose `label == "steg-app"`; none found → `Connection::call("session.new", {label: "steg-app", program: null})` (server decides the program — doc-9 R13, "a pane runs the user's login shell... with a given working directory" — the app never names one) → `Connection::call("tab.list", {target: session_id})`, take the first tab → `Connection::call("pane.list", {target: "{session}/{tab}"})`, take the first pane → `Connection::attach(Some(&format!("{session}/{tab}/{pane}")))`, block-read until the matching `Incoming::Reply`, decode `PaneAttached` → `Connection::open_stream(stream)` (client's own half of decision-2 §3's ordering rule — only after the reply is in hand, confirmed by `wire/connection.rs`'s own doc on `Connection::attach`). The task's return value is everything the main thread needs: the connected `UnixStream`, the `Connection` (now past the handshake, with the attachment's stream open), the `PaneAttached.snapshot`, and the resolved `stream` id. `main.rs` awaits this (via `window.spawn`, which can `.await` a `Task<T>` from `cx.background_executor().spawn`) before building the real terminal `Entity`; until it resolves, the window shows a plain "connecting…" div (still one window, nothing fancier — AC #1 only promises the terminal once attached).
- *The connection, after startup (`client.rs`, owned by the terminal `Entity`, touched only through `Context<Self>`):* the `UnixStream` is switched to non-blocking (`set_nonblocking(true)`) at this point, not before — the handshake above stayed simple and blocking on purpose (identical shape to `crates/server/tests/attach.rs`'s own `connect_and_handshake`/`call_and_read_reply`/`attach` helpers, just run once on a background thread instead of in a test). A `window.spawn`'d background-executor task polls the non-blocking socket every `POLL` tick (recommend 1 ms — see §4's own reasoning for why 200 µs–1 ms is negligible against an 8 ms server tick and an 8.3 ms display refresh, and `spikes/task-1.1-terminal-library/probe-core/src/element.rs`'s own `POLL = Duration::from_micros(200)` is this repository's own prior, already-measured instance of exactly this pattern — steg's own MIT code, not Zed's): a non-blocking `read()` that returns `WouldBlock` does nothing that tick; on real bytes, `connection.receive(&buf[..n])`, then drains **every** queued `Incoming::StreamControl`/`Reply` with a `while let Some(incoming) = connection.poll()` loop before calling `cx.notify()` **once** (§4's own bound) — a `StreamControl` payload is `serde_json::from_slice::<ScreenUpdate>(&payload)`, applied to `model.apply(update)`.
- *Why a plain `std::thread::spawn` reader thread was rejected, named so it isn't silently reinvented later:* `gpui::AsyncApp` (`async_context.rs:17`) holds `app: Weak<AppCell>`, and `AppCell` (`app.rs:61`) is a bare `RefCell<App>` — not a `Mutex`, and `Rc`'s `Weak`, not `Arc`'s. It cannot be sent to a real OS thread at all (the compiler refuses it — `Rc` isn't `Send`), so there is no way to call `weak.update_in` from a thread gpui doesn't itself drive. Everything that touches the entity has to run inside a future gpui's own executor is already running — `window.spawn`/`cx.background_executor().spawn`, as above — which is also exactly the mechanism the spike already proved safe for a tight polling loop.
- *Writes (input bytes, `tab.declare_size`, part 2):* happen synchronously inside whichever `Context<Self>`-bearing call triggered them (`on_key_down`, or the resize check described in §4) — `Connection::send_data`/`Connection::declare_size` build the bytes, `self.stream.write_all(&bytes)` (or a non-blocking write with the small leftover-bytes retry §4 describes) sends them. No second thread, no queue, because everything here is already running on the one thread gpui's executor scheduled it on.

## 2. Drawing (b)

**Cell grid, from the font's metrics.** `metrics.rs`: a `Font` built from `foundations::FONT_TERMINAL` (`&["JetBrains Mono", "SF Mono", "Menlo"]` — first as the family, the rest as fallbacks) at `foundations::TERMINAL.size` (13px); `line_height = foundations::TERMINAL.line_height` (20px, taken directly from foundations rather than re-derived, unlike the spike's own throwaway `font_size * 1.3` stand-in — steg already has the real value); `cell_width` measured once by shaping ten `'M'`s at that size and dividing by ten, exactly `spikes/.../element.rs`'s `Metrics::cell_width` (cached after the first call, invalidated only if the font ever becomes configurable — not in this task). A wide character (`Wide::Wide`) occupies two cell-widths; its `SpacerTail` is skipped when painting (carries no text, per `screen.rs`'s own doc) but still advances the column cursor by one cell, so every run after it lands at the right `x`.

**Runs, not whole rows, and by column position, not byte offset.** `Row = Vec<Run>`, each `Run.text` one grapheme per cell it covers — `SpacerTail` cells contribute no text at all, so a run's *byte length* does not track its *column span*; painting therefore tracks a running column counter across a row's runs (incremented by each run's own cell count, which is its text's grapheme count plus any `SpacerTail`s immediately following a `Wide` run) and paints each shaped run at `x = bounds.origin.x + cell_width * column`, never by accumulating pixel widths from `ShapedLine::width` the way a left-to-right flow layout would — the two can drift apart the moment a cell is invisible or past a reflow boundary, and grid alignment is the one property a terminal can't bend on.

**`CellStyle` → `TextRun`, concretely:**
- `fg`/`bg`: `Some(Rgb{r,g,b})` is the server's own *resolved* 24-bit colour (decision-2 §3: "the server resolves a cell's palette index ... before it reaches here") — `gpui::rgb(colour_to_hex(rgb)).into()`, a data conversion, not a design value, and R120's literal check is scoped to `crates/ui` regardless, so this is not the same thing as a component writing a colour literal. `None` resolves through the `Theme`'s own `TerminalTheme` (`foundations::steg_dark`/`steg_light(theme.session())`, picked by `theme.appearance()`) — `fg`/`bg` from there are the only terminal colours this task hard-codes nowhere; everything else comes from the wire.
- `inverse`: swap the resolved fg/bg (falling back to the theme's own fg/bg first, same as any other cell) before building the `TextRun`, not after — gpui has no "swap these two colours" primitive to defer it to.
- `bold`/`italic`: `Font { weight: FontWeight::BOLD / ..metrics.font, style: FontStyle::Italic / ..metrics.font, ..base }`.
- `underline`: `UnderlineStyle { color: underline_colour.or(fg resolved as above), thickness: px(1.0), wavy: matches!(underline, Underline::Curly) }` — gpui 0.2.2's `UnderlineStyle` (`text_system.rs`) only distinguishes solid/wavy, so `Single`/`Double`/`Dotted`/`Dashed` all paint as solid, honestly stated here as an approximation doc-9's own acceptance set (vim, htop, tmux, Claude Code) does not depend on telling apart, not pretended to be exact.
- `strikethrough`: `StrikethroughStyle` the same shape as `underline`'s, no approximation needed.
- `overline`, `blink`: gpui 0.2.2's `TextRun` has neither a field nor an established technique for either (confirmed from `text_system.rs:733`'s own field list — `len, font, color, background_color, underline, strikethrough`, nothing else). Both are dropped for this task — a documented, deliberate gap, not a silent one; doc-9's acceptance set does not depend on either, and nothing here blocks a later task from painting an extra quad for overline or re-rendering on a timer for blink if one ever needs it.
- `invisible`: an empty-text run the width of what it hides (so the grid still advances), never a `TextRun` with real text at zero opacity.
- `faint`: reduce the resolved foreground's alpha (a cheap, honest approximation — gpui's `Hsla` carries alpha already) rather than drop the flag the engine went to the trouble of reporting.
- `wide`/`link`: `wide` only changes column bookkeeping (above); `link` draws nothing in this task (doc-9 R116's own address-on-demand lookup, and any click/hover behaviour, belongs to TASK-1.57's find/select/links work per doc-9's scope — this task never asks the server for a link's address).

**Cursor:** a quad at `(column * cell_width, row * line_height)`, sized one cell (two if the cell under it is `Wide`) — `Block` filled, `BlockHollow` a 1px-bordered unfilled quad, `Underline` a thin quad at the cell's bottom edge, `Bar` a thin quad at its left edge; drawn only when `cursor.visible`; `blinking` is the same gap as `CellStyle.blink` above, not attempted. Cursor colour is `theme.session()` through the terminal theme's own `cursor` field (`steg_dark`/`steg_light` already set `cursor: session` — never a separate literal).

**What repaints, and the real bound (criterion 5).** The model (`model.rs`) only ever touches the rows a `ScreenUpdate::Delta` names (`rows: Vec<(u16, Row)>`) or replaces the whole `Vec<DrawRow>` on `ScreenUpdate::Full` — O(rows changed), never O(screen) on a delta, which the server already guarantees is at most one coalesced update per 8 ms tick no matter how fast a program prints (decision-2 §4.1: "zero drops, zero resynchronisations" under a 100 MB flood at the default tick — this task feeds no emulator of its own and has no 148 ms-stall failure mode the spike found, because there is no local parse step left to bound). What this task's *own* code must not undo: draining every queued `Incoming` per poll tick before one `cx.notify()` (§1, so a backlog of stale ticks collapses into one repaint instead of one per queued frame — the one place this task could reintroduce an unbounded cost that the protocol itself does not have); and the row-shaping cache (`terminal_element.rs`, identical shape to `spikes/.../element.rs`'s `RowCache`: keyed on a hash of the row's content and style, so an unchanged row costs no reshaping even though the whole grid is repainted — gpui 0.2.2 offers no partial-repaint primitive for a `canvas` element, confirmed by its absence from `window.rs`/`element.rs`'s public surface, so "the whole grid, every frame" is the unavoidable half and "shape only what changed" is the bound this task actually controls). Part 3's own proof is that this bound holds under a flood; part 1 and 2 build it, part 3 measures it.

## 3. Input (c)

**Option: the platform's composed character, not Meta.** Decided, not left open: a dead-key sequence (Option-e then e → é on a US layout) is resolved by macOS's own input context, not by `Keystroke.key_char` alone — confirmed by reading `platform/mac/window.rs:1693-1746`: a key event with no `key_char` yet (a dead key in progress) is routed to `inputContext.handleEvent`, which calls back into gpui's `EntityInputHandler::replace_text_in_range` once the sequence resolves, and *only* if an input handler is registered at all (`with_input_handler`). Meta-as-Option is a different, competing convention (common in other terminals, off by default in most) that would need its own setting later; choosing it now would also mean never implementing the input-handler path below, which is the one piece of this section that needs more than a lookup table. Recommendation stands as composed character; the cost (Alt+b/Alt+f-style readline word motions don't work out of the box) is named in §"For the engineer" above for Bruk to weigh, not hidden in a footnote.

**What that costs in code.** A minimal `EntityInputHandler` on the terminal entity: `marked_text_range`/`selected_text_range` always `None` (no in-place composition display — doc-9's acceptance set doesn't need CJK candidate-window rendering to be pixel-perfect, and real terminal emulators mostly don't attempt it either), `replace_text_in_range`/`replace_and_mark_text_in_range` both forward `new_text.as_bytes()` straight to `send_data` (ignoring the range — there is no text buffer here to splice into, unlike `examples/input.rs`'s real text field), `bounds_for_range`/`character_index_for_point` answer from the cursor's own cell position (so the OS's floating candidate window, when one appears, is positioned near the cursor rather than at the window's origin). `window.handle_input` is called from `paint`, the same call site `examples/input.rs`'s `TextElement::paint` uses (`window.handle_input(&focus_handle, ElementInputHandler::new(bounds, entity), cx)`).

**The key table, for everything the input handler does not intercept** (`keys.rs`, pure function, `fn key_to_bytes(keystroke: &gpui::Keystroke) -> Vec<u8>`, called from `on_key_down` only when `keystroke.key_char.is_none() || keystroke.modifiers.control` — the input-handler path above already owns plain composed text):

| key | bytes | note |
|---|---|---|
| `enter` | `\r` | |
| `backspace` | `\x7f` | |
| `tab` | `\t` | |
| `escape` | `\x1b` | |
| `up`/`down`/`right`/`left` | `\x1b[A`/`B`/`C`/`D` | normal mode only — application cursor mode (`\x1bOA` etc.) is TASK-1.56's, per the brief |
| `home`/`end` | `\x1b[H`/`\x1b[F` | |
| `pageup`/`pagedown` | `\x1b[5~`/`\x1b[6~` | |
| control + letter | `(letter.to_ascii_lowercase() as u8) - b'a' + 1` | `spikes/.../element.rs`'s own mapping, unchanged |
| control + `[` | `\x1b` | control+`[` and plain Escape are conventionally the same byte |
| control + `\` | `\x1c` | |
| control + `]` | `\x1d` | |
| control + `^`/`6` | `\x1e` | |
| control + `_`/`-` | `\x1f` | |
| control + space/`@` | `\x00` | |
| anything else with no `key_char` and no entry above | nothing sent | R29's "a key that is not bound reaches the terminal unchanged" holds trivially here: this app registers zero `KeyBinding`s (no palette, no actions — doc-9/doc-10 M1a scope), so every physical key not swallowed by the table above or the input handler already reaches `on_key_down` with nothing else claiming it first |

**Deliberately out:** application cursor mode, bracketed paste, mouse reporting, the kitty keyboard protocol — named in the task description as TASK-1.56's or later's, and the consequence stated plainly: a full-screen program that relies on any of these (vim's own mouse support, an app expecting bracketed paste) will see plain-mode arrow keys and unbracketed pasted text pasted as a flood of ordinary keystrokes until TASK-1.56 lands; the acceptance set itself (doc-9 R14) is TASK-1.64's to re-check once it does, not this task's to pretend to clear early.

## 4. Size (d)

**Part 1 has no size logic at all, and that's the point of drawing the split line here.** `pane.attach`'s snapshot (TASK-1.47 alone) carries rows and a cursor, nothing else — no `Screen.size`, no `ScreenUpdate::Delta.size` (both are TASK-1.114's additions, confirmed absent from the 1.47 branch's `screen.rs`). Part 1's model therefore derives its one, fixed `(columns, rows)` once, from the attach snapshot itself (`rows.len()` for rows; the first row's own total cell count — summing each `Run`'s cell span, §2's own column bookkeeping — for columns, since every row of a rectangular screen has the same width by construction), and never changes it: no `declare_size` call exists in part 1 at all. This is visibly a fixed grid the kernel already sized at `session.new`, which may not fill the window — stated here, not left for a reviewer to notice unannounced.

**Part 2 adds the real thing.** Columns and rows from pixels: `metrics::columns_rows(viewport: Size<Pixels>, metrics: &CellMetrics) -> (u16, u16)`: `(viewport.width / metrics.cell_width).floor()`, `(viewport.height / metrics.line_height).floor()`, each clamped to at least 1 (TASK-1.114's own plan refuses `columns == 0 || rows == 0` with `BadRequest` server-side — this avoids ever sending that, not relies on being refused for it).

**When it's declared (part 2).** Once on open (right after the terminal entity is built, before the first paint, from the window's own `viewport_size()` at that moment) and again whenever a render observes a different `(columns, rows)` than the last one declared — computed every render (cheap: two divisions), compared against a field on the entity, and only sent on a change. This is simpler than a timer-debounce and already bounded: GPUI's own render cadence is vsync-paced (at most once per display refresh, 8.3 ms at 120 Hz), and decision-2's own measurement puts a control call at 0.06-0.07 ms p95 even under a 100 MB flood in another pane — so "at most once per rendered frame" costs nothing worth a debounce timer for, and a debounce would be the one piece of state in this task that could itself go stale (a declare sent, then superseded by a newer resize, with nothing yet un-sending the first). Recommendation: no explicit debounce; state this reasoning in the task's own doc comment so a reviewer doesn't have to re-derive it, and revisit only if TASK-1.56's own measurement finds a real drag genuinely producing more control calls than this reasoning assumed.

**Drawing at the size the server reports, not the size declared (part 2).** `ScreenUpdate::Delta.size: Option<Size>` and `ScreenUpdate::Full`'s `Screen.size` are what the model's own `(columns, rows)` actually is from here on — decision-6/R91's "latest wins" means another client (none exists yet in this bare task, but the kernel rule doesn't know that) could in principle leave the terminal at a size this window didn't ask for, and the model must draw whatever size the last update reported, never assume its own last-declared value is still current.

## 5. Measurement (e)

**What's stamped, and where.** Four points, all on the main thread (no cross-thread clock reads to reconcile):
1. **key arrival** — the instant `on_key_down` runs, before any byte is sent.
2. **send** — immediately after `self.stream.write_all` returns (the write itself, not the eventual delivery — matches decision-2's own latency definition, "a byte into the pty," one more hop earlier at "a byte onto the wire," which is the one clock this app can actually start).
3. **echo arrival** — the poll tick that applies a `ScreenUpdate` whose cursor position differs from what it was when the keystroke was sent (the spike's own matching method, `latency.rs`'s `Pending.cursor_before`/`note_arrival`, carried over unchanged in spirit). **Its limit, stated plainly, not glossed over:** this attributes "the next update whose cursor moved" to "the keystroke just sent," which is only sound with one keystroke in flight at a time and no concurrent output from the program itself — the spike's own doc says as much ("the probe writes one byte... nothing else moves it while `cat` is the program"). Against a real shell, that holds at an **idle prompt** (nothing else is writing to the pane) and does not hold if a program is mid-output when the sample is taken. Part 3's run is therefore done at an idle shell prompt, one keystroke at a time with the plan's own pacing (the spike's `Plan::interval`, ~80 ms between samples, far clear of even a slow tick), and the notes say exactly that — "measured at an idle prompt, one keystroke in flight at a time," not "measured while using the terminal" — the same honesty decision-3's own record already modelled.
4. **frame painted** — `window.on_next_frame`, the same callback the spike's `Probe::painted` already uses, registered the instant the echo is recognised (step 3), so it captures the *next* frame gpui completes after the echo was applied, including the display's own refresh wait.

**Two durations recorded:** key-to-paint (arrival → the frame in which the model holding the echoed byte was painted) and key-to-frame (arrival → `on_next_frame`'s own callback firing, decision-3's own distinction, carried over by name). Printed as p50/p95 (criterion 4 asks for both explicitly) over a run (recommend the spike's own `Plan::default()` shape — 2000 samples, blocked by 250 — reused as a starting point, not re-derived from nothing), to stdout when the app is launched with an env var (`STEG_MEASURE_LATENCY=1`, say) so a person chooses to run the instrumented path rather than paying its bookkeeping on every ordinary launch — and the numbers from one real run on this machine go in the task's own notes beside doc-9 R19, as data, not as a pass/fail (criterion 4's own wording).

**The honest floor, stated before a single sample is taken, not discovered afterward.** `DEFAULT_ATTACH_TICK` is 8 ms, and the kernel's own pane worker only arms the next tick when real work exists (`maybe_arm_tick`, `pane.rs`), meaning a single keystroke arriving at an idle pane waits up to a **full** 8 ms, not an average half-tick, before the server even computes the update that carries its echo. Add gpui's own paint path (decision-3's measured 2-3 ms p50/~10 ms p95 key-to-paint on a *local* pty with no socket at all) and the display's refresh wait (up to 8.3 ms at 120 Hz, already inside decision-3's key-to-frame number), and the honest expectation going in is that this task's own key-to-paint p95 lands **above** R19's revised 12 ms budget — the 8 ms tick alone is most of it, before anything this task's own code does is even counted. That is doc-9's own open question made concrete, not a defect in this plan: "a measurement, not a pass or fail" (criterion 4) is the right framing, and point 3 above is why a second number at a lower tick isn't this task's to produce.

## 6. Lifecycle (f)

**Closing the window:** drop the entity; its `Drop` (or an explicit teardown called from `on_window_should_close`, gpui's own hook, `window.rs:4329`) calls `Connection::detach` and writes it, then lets the `UnixStream` drop (closing the socket) — no `session.close`, nothing else. The server's own side of this (releasing the attachment, the pane carrying on) is TASK-1.47's, proven there; this task only has to actually call detach rather than just dropping the socket out from under an open attachment, so the server sees a clean `pane.detach` rather than only a dropped connection (both are handled server-side per TASK-1.114's own AC #3/#7, but a clean detach is the honest, intended path when there is time to take it).

**Running the app again:** `startup.rs`'s own `session.list`-then-label-match (§1, §"For the engineer" point 5) finds the same session (`"steg-app"`) and attaches to its first tab's first pane again, same as a fresh connect — there is no special "reconnect" code path distinct from "start," because there is no state this app keeps across runs beyond that label. TASK-1.52 replaces this with the server's own events reaching the app instead of a guess from a fixed label, and with more than one window/session choosing between themselves.

**The connection dropping while the window is open:** the poll task's non-blocking read returns `0` (EOF) or an error other than `WouldBlock` — treated as fatal for this bare task: the model stops updating, the window shows a plain "disconnected" state in place of the grid (reusing the same "connecting…" placeholder div from §1's startup path, not a new one), and nothing attempts to reconnect automatically. Reconnection is explicitly TASK-1.52's ("a second window, and reconnecting" is listed as what this task leaves to it in the task's own description) — stating "disconnect leaves a dead window, by design, until TASK-1.52" here rather than inventing a retry loop this task doesn't need to own.

## 7. Proof (g)

**What is tested without a window, with controls, because it is plain data and functions with no `Window`/`Context` parameter at all** (§1's own file layout is what makes this possible):
- `keys::key_to_bytes` — the table in §3, one test per row plus the "nothing sent" case; control: delete one arm (say, the control-letter arithmetic) and the matching test fails.
- `model::apply` — **part 1:** a snapshot (`ScreenUpdate::Full`) followed by a `Delta` that changes two rows, asserting the resulting `Vec<DrawRow>` only reflects the changed rows and the model's own `(columns, rows)`, read once from the attach snapshot, is untouched by any `Delta` (part 1 never declares a size and there is no `size` field to track yet — TASK-1.47's own `Screen`/`ScreenUpdate` shape); control: make `apply` recompute `(columns, rows)` from a `Delta`'s own rows and the test asserting it stays fixed fails. **Part 2** adds: a `Delta` that reports a `size`, asserting the model's own `(columns, rows)` now tracks the reported size, not the last declared one (§4's own "draws what the server reports" rule); control: make `apply` ignore `Delta.size` and the size-tracking test fails.
- `metrics::columns_rows` — a handful of pixel sizes against known cell metrics, including a size that rounds down to the floor rather than up; control: change `.floor()` to `.round()` and the boundary-case test fails.
- The per-frame bound (criterion 5) — a test over `model::apply` fed a long run of `Delta`s simulating a flood (many single-row updates in a row, as the server's own one-update-per-tick coalescing would actually deliver them — not raw bytes, this app never parses raw bytes) asserting the model never touches more than the rows a given `Delta` named, i.e., that nothing in `apply` ever scans or rebuilds the whole grid on a partial update; control: replace the targeted row write with a full-grid reconstruction and the test's own row-touch counter fails it.
- The size-only-change case TASK-1.114's own plan calls out (a `Delta` with empty `rows` but `size: Some(..)`) is exercised directly in `model::apply`'s own tests, confirming the model still updates `(columns, rows)` from an otherwise-empty delta — not re-proving the kernel's own mechanism (TASK-1.114's job), just confirming this app's model doesn't special-case "empty rows" as "ignore this update."

**What needs gpui at all, and what it needs isn't a window.** None of the above needs `gpui::TestAppContext`/`#[gpui::test]`/the `test-support` feature — confirmed from `app/test_context.rs`/`platform/test/platform.rs`: gpui 0.2.2 does carry a headless `TestPlatform` behind that feature (so a *later* task that wants to test `Element::prepaint`/`paint` integration directly, not just the pure functions behind them, has a real, in-repo-proven option — Zed's own gpui ships this specifically so element logic doesn't need a real window), but this task's own element code (`terminal_element.rs`) is thin enough over `model`/`metrics`/`keys` that nothing in it needs that weight for this task's own proof. If a later reviewer wants the `Element` impl itself exercised, `test-support` is the documented way to do it without opening a real window — noted here so it isn't rediscovered as "impossible" by a future worker.

**What's shown by running it, and what that needs from the engineer.** `just run` already exists (`justfile:208`, `cargo run --package steg-app`) and needs no new recipe. The image and recording (criterion 6) are *not* a `just capture-*` recipe the way the gallery's is: the gallery's capture is deterministic (open, wait for a window id, screenshot, assert a corner pixel) because nothing in it depends on a live program's output; this task's image needs an actual shell prompt and the recording needs an actual typed command, both of which only mean something once a server, a session and a real login shell exist — not worth automating for one PR's own evidence. The engineer runs `just run` once, types a short command, and captures a screenshot and a short screen recording by hand (the same Screen Recording permission `crates/ui/CLAUDE.md` already documents for `capture-gallery`, one-time, interactive) — stated here as what's needed from the engineer, per the brief's own instruction to say so. Nothing in `just check` or CI opens a window: `terminal_element.rs`/`client.rs`/`startup.rs` compile under `just check-packages` the same as any other crate's code, and `main.rs`'s own `Application::run` only ever executes when a person runs the binary, identical in kind to the gallery's own binary/library split (`crates/ui/CLAUDE.md`: "compiling the binary is cheap and proves nothing opens a window by itself").

Every item above gets a named control; none is dropped or assumed.
