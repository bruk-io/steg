## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found twice in review on TASK-1.96 (same task, two successive rounds): a check that claims to see "every leaf key" of a data file is narrower than it claims, because the mechanism meant to prove exhaustiveness shares a blind spot with the thing it's proving.

Round 2 (@bruk.r5): unaccounted_names enumerated themes[]/focus_ring from a fixed field tuple written in the tool, invisible to any field not already in that tuple.

Round 3 (@bruk.r5): the fix (a generic walk, "accounted for if equal to or a dotted descendant of a registered name") replaced the fixed tuple, but _is_accounted_for matches containment by plain string prefix ("path.startswith(f'{name}.')"), and the data file's own keys routinely contain a literal "." inside one name (font.ui, nav.side, radius.surface, ramp/ramp.extended). A new sizes/type key, or a new list entry, whose name textually extends an already-registered name (sizes["palette.footer"], a future ramps entry named "ramp.secondary") is swallowed as if nested inside that name, and reaches no check at all - confirmed by running the real CLI against scratch copies of the real file, each exiting 0 "ok" with the new key silently unverified. The round's own new property-style tests (over "every real leaf path") could not catch this: their universe of leaves is generated by calling the same leaf-walking function that has the bug, so a leaf the walker absorbs under the wrong ancestor never enters either test's own universe - the test checks the registry against the walk, never the walk against the file.

Add to plugins/team/rules/testing.md (or a new rule for review/build on "exhaustiveness checks"): a check that claims to see every key/field/leaf of some data, and a test suite meant to prove that check is exhaustive, must each get their worst-case input from a source independent of the mechanism under test - not from calling the mechanism's own traversal function and checking its output against itself. Separately, for any registry that matches "is-contained-in" by joining names with a separator (such as "."), state plainly that this only works if no name in the data can itself contain that separator - otherwise use a structural (whole-segment, e.g. split-on-"." before compare, or tuple-of-path-components) match, not a string-prefix match.
