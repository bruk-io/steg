## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Asked for by the engineer on 22 November 2026: UI pull requests need an image, and a recording for motion, but workers must not launch the app, inject input or capture the screen on the engineer's machine, so today every UI change waits for the engineer to record it by hand (TASK-1.127, steg PR 95). Unknowns dominate, so the plan starts with a spike and comes back with the route before building. Routes, in the order to try: (A) draw off screen in process and read the frames back, driven by a controlled clock. Checked today: the pinned gpui 0.2.2 has only the test context that does not really draw; newer GPUI lines carry a visual test context and a headless app context that look like this, so A may mean a GPUI upgrade, which is its own decision for the engineer. (B) run the real app on a macOS CI runner against a scenario and capture only its own window there, uploading the result as a build artefact: nothing of the engineer's is on that machine, at the cost of a slow loop. (C) on the engineer's machine, capture only the app's own window by window id in a throwaway home: still puts a window on their screen and needs screen-recording permission, so it is the fallback. The plan names the route, what it costs, and anything that is the engineer's to decide. Licence: read Zed and GPUI to learn the API, copy nothing from Zed's GPL crates.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->

- [ ] #2 A scenario is data in the repository: an explicit pane program with fixed content, a throwaway home, never the login shell, and a scripted timeline (keys, waits, focus changes) on a clock the tool controls, so the same scenario gives the same frames every run and nothing personal can appear

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Spike result, with evidence (no app launch, no window, no input injection, no screen capture - all reasoning and one throwaway cargo project under the scratchpad, not the worktree):

ROUTE A IS REAL AND SPIKED SUCCESSFULLY. Recommend it.

Evidence against gpui 0.2.2 (pinned today): read `~/.cargo/registry/src/.../gpui-0.2.2/src/platform/test/window.rs` - `TestWindow::draw(&self, _scene: &Scene) {}` is a no-op; the atlas fake (`TestAtlas`) never stores real glyph/image bytes. `Scene` and its fields (`src/scene.rs`) are `pub(crate)`, unreachable from outside the gpui crate. `VisualTestContext` (`src/app/test_context.rs`) gives layout and `debug_bounds` only, never pixels. This matches what the repo already found and wrote down itself: `justfile`'s `capture-gallery` recipe comment and `crates/ui/CLAUDE.md` both say plainly that "GPUI 0.2.2 has no way to read a window's pixels except through OS-level screen capture" - which is why the gallery's existing capture goes through a real window, `screencapture -l<window id>`, and a one-time Screen Recording permission grant a worker must never hold. terminal_element.rs:711-722 (TASK-1.136's own prior finding) independently confirms `GlyphId`'s inner field is `pub(crate)` too - not constructible from outside gpui at any feature level. So Route A is closed on the pinned version; it needs the upgrade the task flagged as its own decision.

Newer upstream line, published in this registry as `gpui-pre` (package name), resolved today to 0.3.13 (`"0.3.11"` in Cargo.toml picks the latest compatible; Apache-2.0, same author, `repository = zed-industries/zed`, `package.metadata.gpui-pre.zed-rev = f816e1f...`, i.e. a real later Zed/gpui snapshot under a different crates.io package name). It carries `HeadlessAppContext` (`src/app/headless_app_context.rs`) with `capture_screenshot(window) -> Result<RgbaImage>`, backed by a `PlatformHeadlessRenderer` trait (`src/platform.rs`) that on macOS is `gpui_macos::metal_renderer::MetalHeadlessRenderer` (real Metal, offscreen, `show: false` window, no NSWindow shown) and on Linux is a wgpu renderer - obtained through a new `gpui-pre-platform` crate's `current_headless_renderer()`. The whole thing rides on `TestDispatcher`, so its clock is advanced by the tool (`advance_clock`), not wall time.

SPIKED, not just read: built a throwaway `cargo` project in the scratchpad (`TASK-1.151-spike/`, reverted - never touched the worktree) depending on `gpui = { package = "gpui-pre", version = "0.3.11", features = ["test-support"] }` and `gpui-pre-platform` the same way, with a trivial `Render` view (a div sized full, background `0x204060`, with a `40px` red square child). `cargo build` compiled clean (one unused-import warning only). `cargo run` - a plain `fn main()`, not `#[test]` - ran without the AppKit-off-main-thread SIGABRT that gpui-pre's own ignored `VisualTestAppContext` tests warn about (that warning is specific to the `#[gpui::test]`/worker-thread path; `HeadlessAppContext::with_platform` plus a plain binary's own main thread avoided it entirely) and wrote a 400x300 PNG (200x150 logical at the TestWindow's 2.0 scale factor). Decoded the PNG by hand (stdlib `struct`/`zlib`, the same technique `tools/src/steg_tools/gallery.py` already uses for the real screen capture) and read pixels back: `(10,10)` and `(20,20)` inside the red square both decode to `(255,0,0,255)`; `(200,150)`, outside it, decodes to `(32,64,96,255)` = `0x204060` exactly. Real rendered pixels, not a blank or stub image.

Licence surface: copied the repo's own `deny.toml` into the spike and ran `cargo deny check licenses` against the ~650-crate tree `gpui-pre` + `gpui-pre-platform` + `test-support` pulls (objc2-family, accesskit, usvg/resvg, image, etc.) - result: "licenses ok" (only warnings that three existing allowances - CC0-1.0, CDLA-Permissive-2.0, ISC - go unused by this minimal tree, which is expected; nothing GPL/AGPL, nothing outside the existing allowlist). `image` (new, for `RgbaImage`/PNG) is MIT/Apache-2.0 dual and is already covered.

What this makes cheap, confirmed not guessed: `gpui-pre-0.3.11/Cargo.toml.orig` declares `[lib] name = "gpui"` - the published package is `gpui-pre` but the library's own crate name is still literally `gpui`. So the workspace's one dependency line becomes `gpui = { package = "gpui-pre", version = "0.3.x" }` and every existing `use gpui::...` across crates/app and crates/ui keeps compiling unchanged - this is a dependency swap, not a source-wide rename. A `diff` of `pub fn` names in `window.rs`, `app.rs` and `elements/canvas.rs` between 0.2.2 and this gpui-pre snapshot found the newer line purely additive except one removed function, `paint_shadows` (split into `paint_drop_shadows`/`paint_inset_shadows`), which `grep -rn "paint_shadows"` shows steg never calls. `canvas()`'s own signature is identical. So the paint primitives `terminal_element.rs` actually uses (`canvas`, `paint_quad`, `paint_glyph`, `ShapedLine`) are untouched.

What this does NOT make free, and is this task's real size: gpui-pre moved per-OS platform code out of the monolithic `gpui` crate into separate crates (`gpui_macos`, `gpui_linux`, `gpui_wgpu`, `gpui_windows`, `gpui_web`, `gpui_ios`) plus the dispatcher crate `gpui-pre-platform` that exposes `current_platform`/`current_headless_renderer` - a structural dependency change, not just a version bump, and needs its own `boundaries.toml` entries. `PlatformHeadlessRenderer`/`render_to_image`/`capture_screenshot` are all gated behind gpui's own `test-support` (or `bench-support`) feature - the same feature terminal_element.rs:713-722 already documented as pulling in `rand`, `leak-detection`/`backtrace`, `wayland`/`x11`, which is exactly why that comment said not to add it silently for one test. For a dedicated scenario-capture binary this is now justified, but it must never reach the shipped `steg-app` binary: Cargo's per-target feature unification (resolver = "3", already in the root `Cargo.toml`) only turns a feature on for the targets that actually request it in a given invocation, the same mechanism `capture-gallery` already relies on (`cargo build -p steg-ui --bin gallery` is a separate, explicit build from `cargo build --package steg-app`) - so the plan for the build task is: a second `[[bin]]` that depends on `gpui-pre/test-support`, built and run only by its own recipe, never by `just check`/`just build`'s normal workspace build, proved by `cargo build --bin steg-app` alone showing no test-support-only crates in its own dependency set.

`crates/app` has no `[lib]` target today - `Cargo.toml` has `[package]` and `[dependencies]` only, so `AppWindow` and everything `main.rs` builds (crates/app/src/main.rs:512, `impl Render for AppWindow`) is private to that one binary and not importable by a second bin or crate. The scenario runner needs `src/lib.rs` added to crates/app (re-exporting what a scenario needs: building the window, wiring steg-sdk, the pane kind, etc.), with `main.rs` becoming a thin wrapper over it, and the new scenario bin as a second `[[bin]]` in the same package. This does reach inside the app crate rather than through a public steg API - stated plainly, per the architecture rule: it is justified because the scenario bin still only drives the app through steg-sdk's public API exactly as `main.rs` does today (same consumer path TASK-1.117 already established); the only thing that changes is the entry point, `Application::new().run(...)` swapped for `HeadlessAppContext`. No new capability reaches the CLI or a plugin, and none should - this is a dev-only capture harness, not a steg feature, so it belongs inside crates/app's own package, not behind the public API.

Route B (CI runner capturing its own window): not established and, per AC#1's own wording ("no window on the user's screen... on the machine it runs on"), not needed if Route A holds on the worker's own machine - a local headless recipe already satisfies the acceptance criterion without any CI runner, GPU availability question, or loop-time cost. Leaving GitHub's macOS runner GPU/window-server capability genuinely unestablished; recommend not spending more time on it unless Route A's build task hits something the spike didn't - the spike's `MetalHeadlessRenderer::new()` succeeded on this machine's own GPU, which is the one that matters (the worker's and the engineer's machine are the same one in this team's setup, and the headless renderer never shows a window or asks for screen-recording permission on it).

Route C (capture the app's own real window by id, as `capture-gallery` already does for the ui gallery): reasoned about only, not attempted, per the brief. It already exists and works for the gallery today, but needs a real window on the engineer's screen and a one-time Screen Recording permission grant on that machine - exactly what a worker must never do. Confirmed fallback status only; not attempted.

SCENARIO SHAPE AS DATA (proposal for the build task to pin down):

- Scenarios live at `crates/app/scenarios/<name>.toml` (new directory; mirrors the gallery's own convention of living beside the code it exercises). Each names: an explicit pane program and its argv (never `$SHELL`/the login shell - e.g. a tiny fixed-output binary or `/bin/cat` with a heredoc, so output is identical on every run and nothing from the real environment, like a prompt or a username, can appear); a throwaway `HOME` the tool creates per run and deletes after (the live-run convention this repo already uses elsewhere, but a throwaway one here specifically, never the inheriting-the-real-shell approach); and a scripted timeline of steps - each a key sequence, a wait (as a duration the tool advances `TestDispatcher::advance_clock` by, never a real `sleep`), or a focus change - so the same scenario produces byte-identical frames on every run (the determinism proof: run the recipe twice, diff the PNGs).
- `just capture-scenario <name>` (verb already on `check-recipes`'s list via `capture-gallery`'s precedent) builds and runs the new scenario bin for `<name>`, writing `target/scenarios/<name>/<step>.png` for every scripted step (stills) and, only when the scenario's timeline has more than one step or an explicit "motion" marker, `target/scenarios/<name>/recording.gif`. Never part of `just check` for the same reason `capture-gallery` isn't - it is a UI pull request's own evidence, not a build correctness check - but `just check-packages` should still compile the scenario bin alone, same as it already does for the gallery bin, so nothing opens a (virtual) window by itself under `cargo build`/`cargo test`.
