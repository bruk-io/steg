## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Recommendation: split. This bundles three sub-features of different shape and risk - send (a thin Runtime wrapper and a small, moved key table), capture (a new pane-worker command plus the TASK-1.47 hand-off shape), and wait (a new cross-cutting pending-wait mechanism touching close.rs, events.rs, connection.rs and mod.rs). Each is independently provable with its own negative controls. Splitting TASK-1.90 into three children (send, capture, wait), in that dependency order, is the plan; the design below is written so any of the three can be built and reviewed on its own. If the engineer prefers the bundle, the same design and order of work applies within one task.

What is already built, re-checked against the tree today (the task's own description was written 2026-11-15, before most of this landed):

- The three methods are fully described in crates/sdk/src/description/methods/pane.rs: pane.send (target, text, key - text/key both ValueKind::Text, errors BadRequest/NoSuchTarget/AmbiguousTarget only), pane.capture (target, scrollback switch, Returns::Text, same error set), pane.wait (target, for=exit, timeout, Returns::Record{exit_code}, same error set). Nothing here needs new description plumbing beyond what §4-5 below name.
- crates/server/src/dispatch/pane.rs's "send"|"capture"|"wait" arm, and crates/server/tests/dispatch/cross_cutting.rs's NotYetCase rows (lines 88-90), both answer/expect NotImplementedYet "TASK-1.90" today - exactly the state the task description predicted, unchanged since.
- TASK-1.114 built Runtime::send_input(client, pane, bytes) for an attached client's own stream (Incoming::Data -> connection.rs:490), and PaneHandle::send_input - both require a ClientId that is viewing the pane (Tree::note_input's own precondition) for the "latest client" / status-clearing side effects. Neither is reachable from a one-shot, unattached pane.send call (AC #1 is explicitly "without a client attached"), so this task needs its own, simpler path straight to PaneHandle::send_input with no Tree::note_input call at all - see §2.
- Nothing wraps pane.send/capture/wait at the Runtime level yet (no send_and_dispatch/capture_and_dispatch, no wait interception in connection.rs). TASK-1.89's note that dispatch cannot do I/O is correct and still the reason: dispatch's own signature is &mut Tree, with no access to state.panes (the PaneHandle map) or to a connection's Arc<Outbound>.
- Scrollback: Terminal::oldest_row()/Terminal::page(first, max_rows)/Terminal::scrollback_rows_kept() (crates/kernel/src/terminal.rs) are already public and already used by nothing in production. RowId/Page deliberately do not derive Serialize/Deserialize yet (crates/sdk/src/screen.rs's own doc: "scrollback paging is TASK-1.115's own") - but pane.capture never needs to put RowId/Page on the wire: it renders scrollback to a plain String on the worker thread and returns text. So capture is buildable now, with no overlap with TASK-1.115 (which is about addressable paging as its own API method, over the wire, for an attached stream).
- The only named key-to-bytes table in the repository is crates/app/src/keys.rs's named_key_bytes (and control_byte) - gpui-free pure functions, called by key_to_bytes, which does depend on gpui::Modifiers. doc-16's dependency table is why this table cannot move to the kernel: app depends on sdk and ui only (never kernel), and server depends on kernel and sdk - sdk is the only package both server and app are allowed to depend on, so sdk is the only real home for a table both need without duplicating it. This task moves only named_key_bytes's match arms (not control_byte, not key_to_bytes's Modifiers-based priority logic, which stays in crates/app - out of scope here) into a new, gpui-free module in sdk. Switching crates/app over to call the sdk table instead of its own copy is a named follow-up, not this task: crates/app is off limits here.

Open questions for the engineer, each with a recommended default:

1. doc-2 names no error code for either refusal this task needs (AC #1's "a pane with no running program refuses with the code doc-2 gives" - doc-2 gives none; and pane.wait's own timeout, which doc-2 only describes as CLI exit status 1, section 6). Recommend adding two ErrorCode variants in crates/sdk/src/description/shapes.rs: ProgramNotRunning ("Nothing is currently running in the pane", symmetric with the existing ProgramRunning) for pane.send, and TimedOut ("A wait reached its own timeout before the condition was met") for pane.wait; add both to the two methods' own errors: lists in methods/pane.rs. shapes.rs is a collision risk: TASK-1.88 (building concurrently) is the kind of task that also touches the ErrorCode enum - name both additions explicitly when rebasing. TimedOut needs no special CLI mapping: doc-2's own exit-status table already sends every non-specific error to status 1, which is exactly what section 6 asks for ("a wait that times out is status 1") - noted for TASK-1.50, not acted on here.
2. The key table: recommend the sdk move above, scoped to named_key_bytes's arms only (enter/tab/backspace/escape/arrows/home/end/pageup/pagedown/insert/delete/f1-f12), with the same CANDIDATE_NAMED_KEYS-style coverage test moved alongside it. Recommend NOT adding ctrl-<x>/shift-<x> compound syntax to --key: doc-2 says only "--key <name>", nothing about prefixes, and inventing grammar doc-2 does not give is exactly what drew a Compliance finding on TASK-1.114's review. If Bruk wants ctrl-c etc. reachable from pane.send, that is doc-2's to decide and name, not this task's to guess.
3. Two gaps doc-2's own grammar does not resolve for pane.send: (a) key is described as flag("key", ValueKind::Text, ...) - a scalar - but doc-2 says "--key <name>, may be given more than once." ValueKind has no list kind for an ordinary flag today (only program()'s Argv, a different, positional-after-"--" mechanism). Recommend treating "may be given more than once" as not yet implemented: this task's pane.send accepts at most one --key per call, matching the described scalar shape, and the repeated-flag grammar is left as its own follow-up (a ValueKind change is foundational, not scoped to this task). (b) doc-2 says nothing about text and key given together. Recommend refusing both at once with BadRequest - doc-2 only ever shows them as alternatives ("stdin, or --text, --key"), and refusing avoids inventing an ordering doc-2 never states.

Design

§1. Routing, matching the codebase's existing precedent exactly (confirmed by reading dispatch/mod.rs's own INTERCEPTED_BEFORE_DISPATCH/NOT_YET_NOUNS and Runtime::handle's match):
- pane.send and pane.capture: added to pane::HANDLED in dispatch/pane.rs, with real (not NotImplementedYet) arms that do only the pure, I/O-free part - target resolution, parameter validation, and (for send) the "a program is running" check via the already-exported any_pane_running(tree, &[pane]) - returning Outcome::Nothing (send) or a placeholder Outcome::Text(String::new()) (capture, discarded by the wrapper). Runtime::handle gains two new match arms, "pane.send" => self.send_and_dispatch(...) and "pane.capture" => self.capture_and_dispatch(...), the same shape as start_and_dispatch/close_and_dispatch/move_and_dispatch: call dispatch::dispatch_raw first (brief lock, validation), and only on success perform the real I/O. This is the right shape because, unlike close/move/start, neither send nor capture has any kernel-tree effect at all - the entire effect is against a PaneHandle, which dispatch's signature can never reach; dispatch_raw's role here is purely "validate/resolve under the lock," mirroring how close_and_dispatch already calls dispatch helpers directly for its own pre/post bookkeeping.
- pane.wait: NOT routed through dispatch at all, for the same structural reason pane.attach/pane.detach/tab.declare-size are not (dispatch.rs:96-122, 252-262) - answering it needs a connection's own Arc<Outbound> and the request's own id to reply later, neither reachable from dispatch's signature. Added to connection.rs's handle_request match (next to "pane.attach"/"tab.declare-size") and to dispatch/mod.rs's test-only INTERCEPTED_BEFORE_DISPATCH list plus its own not_implemented_yet arm in dispatch_raw (mirroring pane.attach/detach's existing two lines) so the completeness test still accounts for it.

§2. pane.send (AC #1). Runtime::send_and_dispatch (crates/server/src/runtime/input.rs, alongside the existing send_input/declare_size - the module TASK-1.131 already named for this task):
- Lock, call dispatch::dispatch_raw for "pane.send" (resolves target_pane, refuses NoSuchTarget/AmbiguousTarget/BadRequest the ordinary way, and refuses ProgramNotRunning via any_pane_running if nothing is running in the target - see §open-question-1 for the new code).
- On success, read text/key from the request's own params (both already validated against the description by dispatch_raw's own validate() call) and build the bytes to send: text's own UTF-8 bytes, or the new sdk key table's bytes for key (BadRequest, via dispatch, if both are given - §open-question-3b), then state.panes.get(&pane).send_input(bytes) - a plain, non-blocking mpsc send (PaneHandle::send_input never blocks; no hand-off is needed here, unlike capture).
- Deliberately does not call Tree::note_input: this client is not viewing the pane (note_input's own ClientNotViewingPane precondition would reject it), and AC #1 is explicitly the unattached, one-shot case. No "latest client"/size reapplication and no status-clearing happens for this path - consistent with decision-6/doc-14's own "latest client" model being about attachments, not named as a requirement of this task's own ACs, and flagged above as a question rather than guessed at.
- Response: Response::Ok(Value::Null) (Returns::Nothing).

§3. pane.capture (AC #2). New crates/server/src/pane.rs worker command, PaneCommand::Capture { scrollback: bool, reply: Sender<Result<String, Error>> }, handled on the pane's own worker thread (the terminal is !Send - this is the only thread allowed to touch it, same reasoning as Snapshot/Cwd/Attach):
- terminal.screen() for the active rows (always); if scrollback is true, terminal.oldest_row() then one terminal.page(oldest, max_rows) call sized to scrollback_rows_kept() (bounded by R15's own 10,000-line cap - no loop needed, since page's own max_rows: u16 comfortably covers that count in one call; if it somehow didn't, loop forward by the returned rows' own highest offset+1).
- A new, pure helper (same file) renders Vec<Run> rows to text: each row's runs' text concatenated, trailing whitespace trimmed per row (cells past the last printed character render as blanks the engine pads a row with - trimming avoids capture reading as a wall of trailing spaces; no other published convention exists to follow, so this is this task's own choice, covered by its own test), lines joined by "\n", scrollback (oldest-to-newest) ahead of the screen when asked. Replies with the rendered String.
- PaneHandle gains the TASK-1.47 hand-off shape generalised, not reinvented: a sibling to attach_sender()/AttachSender, e.g. PaneHandle::capture_sender() -> CaptureSender(Sender<PaneCommand>) (a thin clone of the same self.commands), with CaptureSender::capture(scrollback, timeout) -> Result<String, Error> sending PaneCommand::Capture and blocking on recv_timeout(timeout) - unlocked.
- Runtime::capture_and_dispatch (same input.rs module): lock, dispatch_raw validates the target (NoSuchTarget/AmbiguousTarget/BadRequest the ordinary way - no "must be running" refusal: R97 keeps a pane's screen/scrollback readable after its program ends, and capture's own doc-2 row names no such refusal); clone state.panes.get(&pane)'s capture_sender() under the lock; drop the lock; call CaptureSender::capture(scrollback, CAPTURE_TIMEOUT) unlocked - this is the literal hand-off AC #2 asks for ("never under the runtime's lock for longer than a hand-off"), the same shape attach_pane already uses, not CWD_LOOKUP_TIMEOUT's older, weaker "bounded but still locked" pattern (checked: start_and_dispatch does hold the lock across PaneHandle::cwd() today, but that call has a fallback on timeout and predates TASK-1.47's review finding; capture has no such fallback, and the brief's own wording for this task names the hand-off explicitly).
- CAPTURE_TIMEOUT: a new named constant (crates/server/src/pane.rs, beside CWD_LOOKUP_TIMEOUT/RELAY_JOIN_TIMEOUT), proposed at 5s - generous for up to 10,000 rows rendered under contention, and because the call is now unlocked, it only ever stalls the one connection that asked, never the server. On timeout, capture_and_dispatch answers with a new... no new code needed here: this is a case the ApiError set does not yet name either, and since nothing in doc-2 describes a capture timeout at all (unlike wait's, which section 6 names explicitly), propose answering it the same as ErrorCode::EngineFailed ("the terminal engine failed") is documented for - a defensive, should-not-happen path, not a designed-for outcome - flagged for the engineer rather than invented further.
- What capture does against a flooding/non-reading pane (the brief's own question): capture only ever reads the terminal (terminal.screen()/page()), never writes to the program's stdin, so a program that will not read its own input does not affect capture at all - only a program flooding output could make the worker busy handling PtyBytes ahead of a queued Capture command, bounded by CAPTURE_TIMEOUT once the hand-off is unlocked (the server as a whole is never stalled; the one capture call can time out on a sufficiently busy pane, same shape cwd() already accepts for its own 200ms case, scaled up for capture's own larger payload).

§4. pane.wait (AC #3, #4). The core design decision: resolve waits from existing lock-held code paths that already know the outcome, rather than adding any new worker command or any always-present background thread. No thread or registration is needed at all except a short-lived, early-wakeable timer when --timeout is given.

New state (crates/server/src/runtime/mod.rs's State struct): pending_waits: HashMap<PaneId, Vec<PendingWait>>, where PendingWait holds request_id: u64, client_id: ClientId, outbound: Arc<Outbound>, and gate: Option<Arc<WaitGate>> (only Some when a timeout was given). New file crates/server/src/runtime/wait.rs (a seam the module map TASK-1.131 left for this task did not anticipate, since pane.wait is genuinely cross-cutting - named here rather than forced into input.rs) holds:
- WaitGate: the same Mutex<Option<T>> + Condvar shape as pane.rs's own RunGate, minimal: resolve(outcome) (set once, notify_all - a no-op if already set) and await_timeout(dur) -> Option<T> (wait_timeout_while on None, returning whatever was set or None on a real timeout). This is what makes a timer thread wake the instant the wait resolves, never sleeping out the rest of a long timeout after the answer is already known (the RunGate precedent the brief points at).
- Runtime::register_wait(pane, request_id, client_id, outbound, timeout: Option<Duration>) -> WaitDecision - called from connection.rs's "pane.wait" arm under the lock: reads the pane's current program_status (via dispatch::target_pane + the kernel's own Pane::program_status, the same read pane.show already does); if already Ended{exit_code}, returns Immediate(Ok(exit_code)) (answered inline, no registration at all); if NoSuchTarget/AmbiguousTarget/BadRequest, returns Immediate(Err(...)); otherwise (Running) pushes a PendingWait (with a WaitGate only if timeout is Some) into state.pending_waits[pane] and returns Deferred(gate) (or Deferred(None) with no timeout).
- connection.rs's "pane.wait" arm: on Immediate, replies the ordinary way (the existing enqueue-and-return-bool shape every other intercepted method already uses) and keeps reading. On Deferred, returns true (keep reading - the connection's reader thread is never blocked) and, only if a gate came back, spawns one thread that calls gate.await_timeout(timeout); if it returns None (a real timeout, not an early wake from resolution), re-locks and calls a new Runtime::timeout_wait(pane, request_id, client_id) that removes exactly this one pending wait (matched by request_id/client_id, since several waits can be pending on the same pane) if it is still there, and if so enqueues the TimedOut error reply; if it is already gone (resolved first), does nothing. This thread's own lifetime is bounded by min(timeout, time to resolution) - never parked past either.
- Resolution path 1, a natural or forced exit (runtime/events.rs's apply_event_locked, PaneEvent::Exited arm): immediately after state.tree.record_exit(pane, exit_code, now) returns Ok(outcome) - before matching on whether outcome cascades into ExitOutcome::Closed - drain state.pending_waits.remove(&pane) and, for each PendingWait, enqueue Response::Ok({"exit_code": exit_code}) on its own outbound/request_id and, if it has a gate, call gate.resolve(...) so any timer thread for it wakes and exits at once instead of waiting out its own bound. This ordering (exit-code resolution before the cascade match, using the exit_code this arm already has bound, never derived from outcome) is deliberate: a shell pane's own program exiting closes the pane by R94's cascade, and if the close-path resolution ran first a legitimate exit would wrongly answer NoSuchTarget. The pre-existing Err(PaneNotFound(_)) arm in the same function (already documented as provably unreachable here, since close_and_dispatch's own lock has already removed the pane by the time that race was possible) needs no wait handling of its own for the same existing reason - documented inline, not re-derived.
- Resolution path 2, a pane closed while running (runtime/close.rs's close_and_dispatch): under the same lock that already pops scope's handles out of state.panes and closes the tree, drain state.pending_waits.remove(&pane) for every pane in scope (pane.close's one pane, or every pane a tab/session close removes) and enqueue ErrorCode::NoSuchTarget for each, with the same gate-wake as path 1. This is genuinely "at once" relative to the close call: no extra thread, same lock acquisition the close already needed. NoSuchTarget (not a record with no exit_code) is the right shape because doc-2 already treats "the thing you asked about is gone" this way (section 6: "closing something already closed is status 3"), and pane.wait's own Returns::Record{exit_code} makes exit_code a required field with nothing honest to put there for a pane that was closed rather than exited - mirrored by doc-14's own EndReason::Closed carrying no exit code for the identical reason.
- Cleanup on disconnect (connection.rs's ConnectionCleanup::drop): a new call, alongside the existing pane_streams sweep and before deregister_subscriber/disconnect_client, runtime.cancel_waits(client_id) - scans state.pending_waits, removes every PendingWait whose client_id matches, and calls gate.resolve(...) on each removed one with a gate (so its timer thread, if any, wakes immediately and exits without ever trying to write to the outbound that is being torn down in this same Drop). No reply is sent for a cancelled wait - the connection is already gone. This satisfies AC #4's explicit "a client that disconnects while waiting" with zero added threads on that path and a bounded, prompt wake on the one thread that might exist (a timed wait's own timer).
- Nothing here ever touches a pane's own worker thread or its command queue - wait is answered entirely from the drain thread and close_and_dispatch, both already-existing lock holders - so a flooding or non-reading pane (the brief's own question) cannot delay a wait on it at all; wait is immune to exactly the hazard capture must be guarded against.

§6. Tests. New real-pty, real-program tests, each with an explicit program (never the caller's $SHELL/HOME - the account database's shell, same as every other task here), a throwaway socket path in a per-test temporary directory, and every wait through tests/support/mod.rs's run_bounded/wait_child_bounded - no bare sleep where an event exists to wait on. - crates/server/tests/pane_send.rs: (a) send delivers text in order to a real program reading stdin (e.g. cat, asserted via a later capture or an attach snapshot); (b) send --key enter/tab/etc. against a program that echoes what it read, proving the sdk key table's bytes actually reach the pty; (c) send against a pane with no running program (after a real exit) answers ProgramNotRunning and sends nothing (asserted: the terminal's own content is unchanged); (d) send with both text and key given answers BadRequest. Negative controls recorded: (c) with the any_pane_running check removed/inverted, proving the test would catch a silent send; (d) with the refusal removed, proving a client-observable response-shape change, not merely a passing test that never exercised the refusal.
- crates/server/tests/pane_capture.rs: (a) capture of a quiet pane's screen matches a direct PaneHandle::snapshot() read, as text; (b) capture --scrollback after printing past the 10,000-line default includes rows from scrollback, oldest-first, ahead of the screen; (c) capturing a pane whose worker is busy with a single large write (not a flood): a pane running a program that spawns a child or itself never reads stdin (e.g. `sh -c 'sleep 100'`), one pane.send of a text payload sized comfortably past any platform pty input buffer (proposed ~2MB, tuned empirically if needed) to wedge the worker's own write_all inside PaneCommand::Input - then, from a second connection, pane.capture of a different, unwedged pane answers within a short bound (proving the hand-off: the lock was never held across the wedge), and pane.capture of the wedged pane itself either answers once it eventually unwedges or times out within CAPTURE_TIMEOUT without hanging the caller. This is the brief's own required proof for AC #2's "never under the runtime's lock for longer than a hand-off," built without the flood shape TASK-1.123 flagged as fragile (one bounded write, not 120x7MB, and no contention with attach.rs's own binary). Negative control: with capture_and_dispatch changed to hold the lock across the capture round trip (a scratch edit, reverted), the "different pane" check fails within its own bound, proving the test actually exercises the hand-off and is not vacuous.
- crates/server/tests/pane_wait.rs: (a) wait on an already-ended pane (R97-kept) answers at once with the real exit code, no registration; (b) wait on a running pane answers once the program exits, with the real exit code, via a real pty; (c) wait with --timeout on a program that outlives it answers TimedOut within the given bound, and a second wait call afterward (the pane is still running) still works, proving no leaked state; (d) a tab/session force-close while a wait is pending answers NoSuchTarget at once (bounded, well under the close's own multi-second grace window, proving the close-path resolution fires immediately under the lock rather than only after force_end's full grace elapses); (e) the client holding a pending wait disconnects before the pane ever resolves - the next pane.wait from a fresh connection on the same, still-running pane still works correctly afterward (proving cancel_waits actually removed the stale entry, not merely that the process didn't crash) and the test's own thread/handle count returns to its baseline. Negative controls: (b) with the Exited-arm's drain-and-resolve step removed, proving the wait would otherwise hang past a generous bound; (d) with the close-path's own drain step removed, proving the wait would otherwise block for the close's grace window instead of answering at once; (c) with WaitGate::resolve not called on timeout, proving the timer thread would otherwise sleep out its full bound even after an unrelated resolution (if that path is reachable in the test as built - note explicitly if it is not, rather than claim an unproven case).
- A small kernel/sdk-level unit test, wherever the engineer prefers it to live, that the moved key table's named_key_bytes arms, lifted into sdk, answer identically to the ones still in crates/app/src/keys.rs for every one of the existing CANDIDATE_NAMED_KEYS entries - not a behaviour change, a guard that the move was a straight lift.

Risks:
- The pending_waits mechanism is new, cross-cutting state with no existing precedent in this codebase beyond RunGate's own narrower shape (one gate per pane's run, not a dynamic set per pane) - the biggest design risk in this task, and the reason it heads the recommended split.
- CAPTURE_TIMEOUT and the ~2MB wedge-write size are both this task's own first guesses, not measured; expect to tune both empirically while building, the same humility this codebase's other timing constants were built with.
- Moving named_key_bytes to sdk, even as a pure lift, touches a file (crates/app/src/keys.rs) the brief marks off limits "unless raised as a question" - this plan raises it as §open-question-2 rather than touching crates/app directly; the new sdk module is additive only until app is switched over by a follow-up task.
