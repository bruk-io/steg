## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Asked for by the engineer on 22 November 2026: UI pull requests need an image, and a recording for motion, but workers must not launch the app, inject input or capture the screen on the engineer's machine, so today every UI change waits for the engineer to record it by hand (TASK-1.127, steg PR 95). Unknowns dominate, so the plan starts with a spike and comes back with the route before building. Routes, in the order to try: (A) draw off screen in process and read the frames back, driven by a controlled clock. Checked today: the pinned gpui 0.2.2 has only the test context that does not really draw; newer GPUI lines carry a visual test context and a headless app context that look like this, so A may mean a GPUI upgrade, which is its own decision for the engineer. (B) run the real app on a macOS CI runner against a scenario and capture only its own window there, uploading the result as a build artefact: nothing of the engineer's is on that machine, at the cost of a slow loop. (C) on the engineer's machine, capture only the app's own window by window id in a throwaway home: still puts a window on their screen and needs screen-recording permission, so it is the fallback. The plan names the route, what it costs, and anything that is the engineer's to decide. Licence: read Zed and GPUI to learn the API, copy nothing from Zed's GPL crates.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria

- [ ] #2 A scenario is data in the repository: an explicit pane program with fixed content, a throwaway home, never the login shell, and a scripted timeline (keys, waits, focus changes) on a clock the tool controls, so the same scenario gives the same frames every run and nothing personal can appear

- [ ] #4 The team's rules say a UI pull request's image comes from this tool, and the worker brief's ban on launching the app stays

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Spike result, with evidence (no app launch, no window, no input injection, no screen capture - all reasoning and one throwaway cargo project under the scratchpad, not the worktree):

ROUTE A IS REAL AND SPIKED SUCCESSFULLY. Recommend it - but see the provenance finding below, which changes WHICH package to depend on, not whether Route A is right.

Evidence against gpui 0.2.2 (pinned today): read `~/.cargo/registry/src/.../gpui-0.2.2/src/platform/test/window.rs` - `TestWindow::draw(&self, _scene: &Scene) {}` is a no-op; the atlas fake (`TestAtlas`) never stores real glyph/image bytes. `Scene` and its fields (`src/scene.rs`) are `pub(crate)`, unreachable from outside the gpui crate. `VisualTestContext` (`src/app/test_context.rs`) gives layout and `debug_bounds` only, never pixels. This matches what the repo already found and wrote down itself: `justfile`'s `capture-gallery` recipe comment and `crates/ui/CLAUDE.md` both say plainly that "GPUI 0.2.2 has no way to read a window's pixels except through OS-level screen capture" - which is why the gallery's existing capture goes through a real window, `screencapture -l<window id>`, and a one-time Screen Recording permission grant a worker must never hold. terminal_element.rs:711-722 (TASK-1.136's own prior finding) independently confirms `GlyphId`'s inner field is `pub(crate)` too - not constructible from outside gpui at any feature level. So Route A is closed on the pinned version; it needs the upgrade the task flagged as its own decision.

SPIKED, not just read: built a throwaway `cargo` project in the scratchpad (`TASK-1.151-spike/`, reverted - never touched the worktree) depending on the headless-rendering capability (details below), with a trivial `Render` view (a div sized full, background `0x204060`, with a `40px` red square child). `cargo build` compiled clean (one unused-import warning only). `cargo run` - a plain `fn main()`, not `#[test]` - ran without the AppKit-off-main-thread SIGABRT that this code's own ignored `VisualTestAppContext` tests warn about (that warning is specific to the `#[gpui::test]`/worker-thread path; `HeadlessAppContext::with_platform` plus a plain binary's own main thread avoided it entirely) and wrote a 400x300 PNG (200x150 logical at the TestWindow's 2.0 scale factor). Decoded the PNG by hand (stdlib `struct`/`zlib`, the same technique `tools/src/steg_tools/gallery.py` already uses for the real screen capture) and read pixels back: `(10,10)` and `(20,20)` inside the red square both decode to `(255,0,0,255)`; `(200,150)`, outside it, decodes to `(32,64,96,255)` = `0x204060` exactly. Real rendered pixels, not a blank or stub image.

PROVENANCE OF THE DEPENDENCY (added at the team lead's explicit request before this goes to the engineer - checked against crates.io's own API and GitHub's, not assumed):

The spike above used a crate published on crates.io under the name `gpui-pre` (plus split crates `gpui-pre-platform`, `gpui-pre-apple`/`gpui_apple`, etc.) - `[lib] name = "gpui"`, so source-compatible, but NOT the official `gpui` crate. Checked `crates.io/api/v1/crates/gpui-pre` and its `/owners`: every one of `gpui-pre`, `gpui-pre-platform`, `gpui-pre-apple` is owned solely by one crates.io account, `huacnlee` (Jason Lee) - the same account that owns `gpui-component`/`gpui-kit`, a well-known third-party GPUI component library. This is NOT the `zed-industries` org. The official `gpui` crate's owners (`crates.io/api/v1/crates/gpui/owners`) are three named Zed engineers (`maxbrunsfeld`, `mikayla-maki`, `MrSubidubi`) plus the team `github:zed-industries:crates-io`. `gpui-pre`'s own metadata self-declares `repository = "https://github.com/zed-industries/zed"` and a `zed-rev` commit - but crates.io does not verify that field against anything; it is the republisher's own claim.

Checked the claim, not just read it: fetched `crates/gpui/src/scene.rs` and `crates/gpui/src/app/headless_app_context.rs` straight from `github.com/zed-industries/zed` at the exact commit `gpui-pre` 0.3.11 claims (`f816e1f9263e3a8ef63c4baaa02e1441ce1c6038`, via `raw.githubusercontent.com`) and diffed them against the cached `gpui-pre-0.3.11` source: both byte-identical, `diff` exit 0. So for the two files sampled, this is a faithful, unmodified snapshot of real Zed source, not a rewrite - and the capability itself (`HeadlessAppContext`/`capture_screenshot`) is genuinely Zed-authored code that exists in Zed's own real git history, confirmed directly against GitHub, not invented by the republisher. The one local change found is a single documented comment in `gpui-pre-apple`'s `build.rs` ("the gpui sources it reads are vendored under vendor/gpui") plus a byte-identical vendored copy of a few source files (diffed clean against the same files in the main crate) - this is `cbindgen`'s Metal shader-binding codegen needing to find gpui's source on disk by path, which breaks under a renamed package; the vendored copy is a path workaround, not a code change. Not exhaustive - only two files were checked directly against upstream, not the whole crate.

The official `gpui` crate (zed-industries-owned) has no newer version: crates.io's own `max_version`/`newest_version` for `gpui` is still `0.2.2`, same as steg's pin, and does not include `HeadlessAppContext`. So "use the official crate" is not actually an option today - the capability exists in Zed's own repository but Zed has never published a `gpui` release past 0.2.2 to crates.io that carries it.

Third option checked: a git dependency pinned to a commit of `zed-industries/zed` directly (`gpui = { git = "https://github.com/zed-industries/zed", rev = "...", package = "gpui" }`), getting Zed's own code with no republishing intermediary and no third-party crates.io account in the trust chain at all. Cost, checked rather than guessed: GitHub's own API reports the zed-industries/zed repository at ~546 MiB (`"size": 559418` KB) - a git dependency clones the whole monorepo (Cargo does not do a sparse per-crate checkout of a git source) to reach the one crate inside it, a real one-time cost (cached afterwards in `~/.cargo/git/`, same as any git dependency). `cargo deny check licenses` does not care whether a dependency's source is a registry or git - it reads Cargo's own manifest metadata either way, and the real `gpui` crate's own `Cargo.toml` already declares `license = "Apache-2.0"`, so the licence check should behave the same for either option (both are the same commit lineage, so the same ~650-crate dependency tree, same licences - already spiked clean with `cargo deny check licenses` reporting "licenses ok" against this exact tree). steg's own `deny.toml` has no `[sources]`/`[bans]` section today, and `just check`'s `deny` recipe runs only `cargo deny check licenses` - no existing policy blocks either option on sources grounds. Whether `boundaries.toml`/`steg-boundaries` (`tools/src/steg_tools/boundaries.py`) copes with a git-sourced dependency the same as a registry one was not fully confirmed (it appears to key off package names declared in Cargo.toml, not source kind, but this needs a real check in the build task, not an assumption).

RESTATED RECOMMENDATION, with provenance weighed in - a question for the engineer:

Given the choice is between (i) a registry crate maintained by one unaffiliated individual who republishes Zed snapshots under a different name (gpui-pre), with the actual code verified faithful for the files sampled but not exhaustively, and no Zed oversight of what gets published or when; and (ii) a git dependency pinned to an exact commit of Zed's own real repository, with the same code, the same licence, and no third-party account in the chain, at the cost of a large one-time monorepo clone and an unconfirmed (but likely fine) interaction with `boundaries.toml`/`steg-boundaries`: my recommended default is now (ii), the git pin, specifically for the provenance reason - moving steg's whole UI dependency onto a single unaffiliated maintainer's unaudited republish, however faithful it spot-checked today, is an ongoing trust relationship (that account could publish a future snapshot nobody checks the same way, or stop maintaining it), where a commit-pinned git dependency on Zed's own repository has no such intermediary at all. The registry route is the fallback if the git-monorepo clone cost or a `boundaries.toml`/tooling friction turns out to be worse in practice than it looks from here - that is a build-task-stage risk to confirm, not a reason to default away from the git pin now.

The rest of this plan - the route comparison (A vs B vs C), the cost of moving off `gpui` 0.2.2 (crates/app needing a lib target plus a second `[[bin]]`, the `test-support` feature staying off the shipped binary, the scenario data shape, the size split into (a)/(b)/(c)/(d), and the proof per acceptance criterion - is unchanged by this finding except decision 1 below, which now names the git pin as the default instead of the `gpui-pre` registry crate; (a)'s own size may grow slightly to account for pinning and vendoring the git dependency's lockfile entry and confirming `steg-boundaries` handles it, but it is still the same single piece of work, not a new split.

SCENARIO SHAPE AS DATA (proposal for the build task to pin down):

- Scenarios live at `crates/app/scenarios/<name>.toml` (new directory; mirrors the gallery's own convention of living beside the code it exercises). Each names: an explicit pane program and its argv (never `$SHELL`/the login shell - e.g. a tiny fixed-output binary or `/bin/cat` with a heredoc, so output is identical on every run and nothing from the real environment, like a prompt or a username, can appear); a throwaway `HOME` the tool creates per run and deletes after; and a scripted timeline of steps - each a key sequence, a wait (as a duration the tool advances `TestDispatcher::advance_clock` by, never a real `sleep`), or a focus change - so the same scenario produces byte-identical frames on every run (the determinism proof: run the recipe twice, diff the PNGs).
- `just capture-scenario <name>` (verb already on `check-recipes`'s list via `capture-gallery`'s precedent) builds and runs the new scenario bin for `<name>`, writing `target/scenarios/<name>/<step>.png` for every scripted step (stills) and, only when the scenario's timeline has more than one step or an explicit "motion" marker, `target/scenarios/<name>/recording.gif`. Never part of `just check` for the same reason `capture-gallery` isn't - it is a UI pull request's own evidence, not a build correctness check - but `just check-packages` should still compile the scenario bin alone, same as it already does for the gallery bin, so nothing opens a (virtual) window by itself under `cargo build`/`cargo test`.
