## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Asked for by the engineer on 22 November 2026: UI pull requests need an image, and a recording for motion, but workers must not launch the app, inject input or capture the screen on the engineer's machine, so today every UI change waits for the engineer to record it by hand (TASK-1.127, steg PR 95). Unknowns dominate, so the plan starts with a spike and comes back with the route before building. Routes, in the order to try: (A) draw off screen in process and read the frames back, driven by a controlled clock. Checked today: the pinned gpui 0.2.2 has only the test context that does not really draw; newer GPUI lines carry a visual test context and a headless app context that look like this, so A may mean a GPUI upgrade, which is its own decision for the engineer. (B) run the real app on a macOS CI runner against a scenario and capture only its own window there, uploading the result as a build artefact: nothing of the engineer's is on that machine, at the cost of a slow loop. (C) on the engineer's machine, capture only the app's own window by window id in a throwaway home: still puts a window on their screen and needs screen-recording permission, so it is the fallback. The plan names the route, what it costs, and anything that is the engineer's to decide. Licence: read Zed and GPUI to learn the API, copy nothing from Zed's GPL crates.

1. RECORDING OF MOTION - FRAME SAMPLING

A "wait" step does not itself make a frame: the harness samples frames at a fixed interval of its own clock (`TestDispatcher`'s virtual time, advanced by `advance_clock`) across every wait, not just once at the end. Default interval: 100ms (10 samples/second - the cadence the team lead named for the dissolve), overridable per scenario (`sample_interval_ms` in the scenario's own `.toml`). For each 100ms (or configured) tick of virtual time the harness advances, it calls `cx.run_until_parked()` (pure virtual-dispatcher draining, no real sleep) to let any pending repaint settle, then captures a frame.

How stills relate to the sampled frames: every scripted step boundary (a key sequence finishing, a wait ending, a focus change landing) is one of the fixed-interval sample points by construction - the harness rounds a step's own wait duration up to the sampling interval, so a step boundary always lands on a sample. The still PNGs the recipe writes (`target/scenarios/<name>/<step>.png`) are named subsets of the sampled frames - one per scripted step, at the step's own boundary sample. The recording (`recording.gif`) is the full ordered sequence of every sampled frame across the whole scenario, not just the step-boundary ones, with each GIF frame's own delay set to the sampling interval that produced it.

2. DETERMINISM AGAINST REAL TIME

The pane program, the pty, the local server and the kernel run on real OS threads and real wall-clock time, outside `TestDispatcher` entirely - advancing the dispatcher's virtual clock does nothing to make their output arrive sooner, and nothing stops the harness from capturing before it has. The harness must never poll (checking in a loop with a sleep) and never sleep a fixed guess - it waits on a bounded event tied to the real arrival: the same shape gpui's own `TestAppContext::condition`/`Entity::next_notification` already use in the version this spike read (a predicate race against a bounded timer, woken by the real notification when the model updates, not by re-checking on a cadence) - concretely, waiting for the client's model to hold the scenario's own expected screen content, or steg-sdk's own bounded pane-wait primitive if one already exists for this (to be confirmed in the build task, not assumed here), each with its own timeout so a stuck scenario fails loudly instead of hanging. Only once that bounded wait resolves does the harness advance the virtual clock or capture a sample.

Read `crates/app/src/terminal_element.rs` and `main.rs` on `origin/main` (PR 95, merged) to answer the team lead's direct question - how the dissolve's own timer and phase are driven: `CursorFadeState.cycle_started_at` is `std::time::Instant` (`terminal_element.rs`, `Default::default()` and `show_whole()` both call `Instant::now()`); `paint_cursor_fade` computes `fraction_through_cycle` from `cycle_started_at.elapsed().as_secs_f32()` - `Instant::elapsed()`, the real OS monotonic clock, not a gpui-owned or virtualisable value. The *wake itself* is scheduled through gpui's own `BackgroundExecutor::timer` (`schedule_fade_wake`), which the harness's `TestDispatcher` can fire at a chosen virtual instant - but the *phase painted once that wake fires* is still computed from real elapsed wall-clock time since `cycle_started_at`, which the harness's virtual clock advance does not move. So advancing the dispatcher's clock to make a wake fire "early" in virtual time does not make the dissolve paint the phase that virtual duration would imply - it paints whatever phase the real wall-clock elapsed time (however little, since no real sleep happened) implies instead. The dissolve would not reach a chosen phase deterministically under this harness as it stands today - frames would depend on incidental real-time scheduling, not on the scenario's own scripted waits. This is a product change to TASK-1.127's own shipped code, not something this harness task can work around: `CursorFadeState`/`paint_cursor_fade` would need to source "now" from something the scenario harness can set deterministically (for example, a `now` the window or app already carries for this purpose, if the newer GPUI line exposes one, or a parameter threaded through painting that defaults to `Instant::now()` in production and is fixed under the harness) instead of calling `Instant::now()`/`.elapsed()` directly. Stating this plainly rather than working around it silently: it is its own line in the dissolve scenario's own plan - TASK-1.155, which carries that scenario's own fidelity criterion - or, if the change turns out bigger than one function, its own task depending on this one the same way TASK-1.155 already does. This harness task does not need to fix it: it only needs to expose whatever clock-control primitive TASK-1.155's own fix ends up needing (see the short paragraph below).

(b) THE HARNESS - this task's own scope

- `crates/app` grows `src/lib.rs` (re-exporting what a scenario needs - building the window, wiring steg-sdk, the pane kind) with `main.rs` becoming a thin wrapper over it. Reaches inside the app crate rather than through a public steg API - justified per the architecture rule because the scenario runner still only drives the app through steg-sdk's public API exactly as `main.rs` does today; only the entry point changes, and no new capability reaches the CLI or a plugin.

DECISION 2, REVISED: my earlier decision 2 (a second `[[bin]]` in `crates/app`) does not hold. TASK-1.154's planning found the mechanism and I accept it: Cargo resolves features per *package*, not per target, so a second `[[bin]]` needing `gpui_platform`'s `test-support` feature would force that feature into `crates/app`'s one `[dependencies]` table, reaching the shipped `steg-app` binary too. `capture-gallery`'s `gallery` bin doesn't prove otherwise - it turns on no feature at all, so it never exercised this limit. TASK-1.154 proves the real mechanism instead: `gpui_platform` named twice in `crates/app/Cargo.toml` - once in `[dependencies]` (no `test-support`, the real app's own platform) and once in `[dev-dependencies]` (`features = ["test-support"]`) - with a `[[example]]` target as the only thing that can see the dev-dependency edge. Two ways to use that same mechanism for this task's own, much larger scenario runner, each with what it costs:

(i) THE SCENARIO RUNNER AS AN `[[example]]` IN `crates/app`, on `[dev-dependencies]` - the same mechanism TASK-1.154 proves, reusing its own `test-support` edge rather than adding a second one. Cost: no new workspace member. But not quite "no new boundaries entry" in every case: TASK-1.154's own plan found that `steg-boundaries` reads declared dependencies and features off every dependency kind alike, dev included - so any dependency the scenario format itself needs beyond `gpui_platform` (for example a TOML-parsing crate for the scenario file) still needs its own `boundaries.toml` entry and reason as a dev-dependency, exactly as if it were a normal one; only `gpui_platform`'s own entry is already covered by TASK-1.154. `examples/` is also a readability cost worth naming: the convention there is a short, illustrative snippet (TASK-1.154's own `headless_smoke.rs`), not a scenario-file parser, a bounded-wait synchronisation helper, a fixed-interval sampler and GIF assembly - all of which this task's own harness needs and none of which `headless_smoke.rs` does.

(ii) A SEPARATE WORKSPACE MEMBER for the scenario runner, depending on `crates/app`'s own lib target and taking its own normal (not dev) dependency on `gpui_platform` with `test-support` - explicit isolation: a different package entirely, so `cargo tree -p steg-app` never shows the runner's own dependencies (TOML parsing, GIF assembly, whatever else) at all, not even as dev-deps, and every one of them gets its own `boundaries.toml` entry and reason up front rather than folded into `crates/app`'s manifest. Cost: a new crate, the boundaries.toml entries just named, and the same public-enough `lib.rs` surface on `crates/app` either option already needs.

RECOMMENDED DEFAULT: (ii), the separate workspace member - matching TASK-1.154's own stated recommendation for this exact question. Reason: this harness is not a one-off smoke test proving one API call works (TASK-1.154's own `headless_smoke.rs`) - it is real, growing software (a scenario file format and its parser, the bounded-wait primitive, the fixed-interval sampler, GIF assembly) that TASK-1.155 and whatever scenario comes after it will keep extending. Putting that in `crates/app/examples/` either misleads a reader about what an example is, or grows `crates/app`'s own manifest with dependencies that have nothing to do with the app itself or with TASK-1.154's own minimal proof of the isolation mechanism. A separate crate keeps `crates/app`'s manifest stable (only TASK-1.154's own two-table `gpui_platform` entry and its smoke-test example touch it, same as before this task exists) and makes every one of the runner's own dependencies a reviewable, reasoned `boundaries.toml` line, matching the architecture rule's own stated philosophy that a dependency edge is a statement about these boundaries. Fallback: (i), if a new crate is judged too heavy for this task's own size once its build phase starts pricing it - the engineer's call either way, since both actually work.

NEGATIVE CONTROLS THIS TASK RECORDS (failing, then the real passing run, at the final head - the team's own proof rules ask for a recorded run each way, not a description of one; the build task records these, this plan names what each proves and traces it to its mechanism):

(a) Remove the bounded wait on pane output (point 2), so the harness advances the clock and captures right after sending a key instead of waiting for the model to hold that key's echo. Honestly, a naive version of this control is racy, not deterministic: the real pty/kernel/server round trip takes some nonzero real time, but if the control still yields to the scheduler at all before capturing (even once, through `run_until_parked` or any other await), that yield can incidentally give the real I/O enough time to land anyway, so the control might pass by accident on some runs and not others - not something to record as a negative control, since a flaky failure proves nothing about the mechanism. The deterministic variant: structure the control so capture happens with no yield point at all between sending the key and capturing - not a shorter wait, no wait whatsoever, so the executor never has a chance to run the task that would apply the real pane's update to the model. Since the pty round trip can only ever be observed by the model through a task scheduled on the foreground executor, and this variant never lets that task run before capturing, the captured frame deterministically still shows the pre-key state, every time, by construction, not by timing luck. Traced to its mechanism: this is what proves the harness actually needs the bounded wait at all, rather than working by the real round trip happening to be fast enough in practice.
(b) Remove the fixed-interval sampling (point 1) - revert to capturing one frame per scripted step only, the behaviour this plan replaced. The quiet wait in the proof scenario (no key sent, no pane activity, nothing but time passing) then yields exactly one frame for that step instead of several. Deterministic with no race involved: it is a plain count of frames produced for one step, gated only by whether the sampling loop exists, not by any real-time arrival. Traced to its mechanism: this is what proves the recording actually carries motion sampled at the interval, not an accident of there being more than one scripted step.
(c) Corrected to match TASK-1.154's own mechanism and check, not a separate one this task invents: temporarily add `features = ["test-support"]` to the *normal* `gpui_platform` entry in `crates/app/Cargo.toml` (its `[dependencies]` table, not `[dev-dependencies]`) - the same leak TASK-1.154's own AC#3 negative control rehearses - and re-run TASK-1.154's own check, `cargo tree -p steg-app -e normal,build -f "{p} {f}"` grepped for `test-support`, now once this task's own scenario runner exists alongside it. Record the match (naming `gpui_platform`/`gpui`/`gpui_macos`), then revert and show the same command empty again. Deterministic, no timing involved: a build-graph membership check, not a runtime one. Traced to its mechanism: this is what proves adding this task's own runner - either shape (i)/(ii) above - did not quietly widen what counts as `steg-app`'s own dependency set, not a new check invented for this task.
